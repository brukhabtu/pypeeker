# Roadmap plans — post-migration lifts

Four implementation plans for the remaining architectural lifts, each defining its own
execution workflow (same shape as the seven migration phases: implementer stage(s), haiku
gate with bounded fix loop, parallel opus adversarial review lenses, fixer, final gate).
Designed by a 4-planner + 1-sequencer workflow. Execution is one dynamic workflow per
plan (per PR-slice for the multi-PR plans), with joint review gating each launch.

The sequencing section at the end is normative: it re-orders Plan B after Plan A,
rebases Plan D's engine stage onto the overlay substrate, and lists per-plan
adjustments that supersede the corresponding plan text where they conflict.

## Plan A — overlay-unification

### ITEM A — One execution path: route planner byte-reads through the store, swap the batch mirror for OverlayIndexStore, and collapse submit_intent's single-intent fast path

**Scope:** **L overall — and it must split into three PRs, in this order.** PR1 (store-read port): **M** — 14 call sites across 10 modules plus 3 new store methods, entirely mechanical, and provably faithful because the whole existing suite must pass with zero test edits; the only judgment calls are extract-method's `read_text()` decode and `AnchorIndexFresh`'s hash comparison. PR2 (mirror → overlay): **M/L** and the judgment-heavy one — `run_batch`, `flatten_batch`, `_apply_to_mirror`, `BatchResult`, `privatize`, `cli.py:batch`, plus the ~30 mechanical test-call-site migrations and the `TestMaterializeMirror` replacement. PR3 (fast-path collapse): **M** — three additive dataclass fields, one rewritten function, one deleted branch, and the doc updates, but it is where every frozen CLI contract is at risk and so needs the most review. Splitting is not optional: PR1's value is precisely that it is a bisectable, behavior-identical checkpoint where a hash regression cannot hide behind a substrate change, and PR2 is the only PR that touches test files in bulk, so keeping PR3's diff test-free (bar one rename) is what makes "no contract moved" auditable.

### Problem
architecture.md's "Everything is a batch" (structural item 3) is marked landed, but the codebase still has two execution substrates, and the third bullet of the "Walls this makes visible" list names exactly this: "The temp-dir mirror is a stopgap for planners reading bytes off disk; once planners read through the store, OverlayIndexStore replaces the mirror and batch-of-one costs nothing." Today `app.submit.submit_intent` materializes a lone intent directly against the real store while `refactor.batch.run_batch` copies the whole indexed project into a temp directory first — two code paths, two failure surfaces, and a per-refactor `shutil.copyfile` of every indexed file plus a full re-save of every FileIndex. The root cause is narrow and fixable: fourteen call sites in `refactor/` read source bytes as `store.project_root / path` and hash them as `IndexStore.compute_file_hash(Path)`, both of which bypass any in-memory layer. Closing this lets the walls list shrink by one, makes `move-symbol`-style file birth/death a tractable follow-up (the overlay already has `write_file`/`delete_file` tombstones), and removes the only reason `submit_intent` and `run_batch` differ.

### Design
Three sequential, independently-shippable PRs. Each lands green on pytest + ruff + self-lint.

## PR1 — Store-read port (behavior-preserving, mirror untouched)

Add to `storage/index_store.py:IndexStore` the read half of the surface the overlay already has:
- `read_file(source_path: str) -> bytes` — `(self._project_root / source_path).read_bytes()`
- `file_exists(source_path: str) -> bool`
- `file_hash(source_path: str) -> str` — `hashlib.sha256(self.read_file(p)).hexdigest()`

and add `file_hash` to `OverlayIndexStore` as `sha256(self.read_file(p))`, so it is overlay-aware where the inherited-by-name static `compute_file_hash(Path)` is not. Keep the static `compute_file_hash(Path)` for `applier.py` and delete nothing.

Rewrite all fourteen inventoried sites to `store.read_file(p)` / `store.file_exists(p)` / `store.file_hash(p)`. Two judgment points: `ExtractMethodPlanner.plan` L236's `read_text()` becomes `store.read_file(p).decode("utf-8")` (matching every other planner, which is already bytes-first and utf-8); `AnchorIndexFresh` compares `index.file_hash != store.file_hash(self.file_path)`. Collapse the two `getattr(store, "read_file", None)` duck-typing sites (`hierarchy.from_store` L206, `materialize_mirror` L511) to direct `store.read_file(...)` calls now that both store classes have it.

**Why this is its own PR:** it touches 14 sites across 10 modules in `refactor/` + `analysis/` and must produce byte-identical output. With the mirror still in place, a plain `IndexStore` rooted at the mirror answers `read_file` from the mirror, so *every existing test passes unmodified* — that is the proof the port is faithful, and it is worth having as a clean bisect point before any substrate change. Rejected alternative: doing this inside the cutover PR, where a hash regression and a substrate regression would be indistinguishable.

## PR2 — Mirror → overlay

`run_batch` builds `OverlayIndexStore(store)` instead of `materialize_mirror(store, root)`. Consequences, each a deliberate decision:

- **Transaction-store routing (the highest-risk change).** Today `TransactionStore(mirror.project_root)` is implicitly a throwaway because `project_root` is the temp dir. Under the overlay `project_root` is the REAL root, so the same line would write every simulated intermediate transaction into the user's `.pypeeker/transactions/`. `run_batch` therefore takes an explicit `tx_store: TransactionStore` parameter; `cli.py:batch`, `plan_privatize`, and `submit_intents(n≥2)` pass a scratch store under a temp dir — the discipline `check_fixes._scratch_transactions` already established and can be lifted into `storage` or reused from `app`. Never derive it from `store.project_root`.
- **Freshness/hash semantics replace file copies.** The mirror gave freshness by construction (copy bytes, re-`save` the index, so `is_stale` was False). The overlay gives it by layering: reads fall through to disk until `write_file`, after which `is_stale` hashes overlay bytes against the last saved in-memory `FileIndex` — `rebind_source` (already store-agnostic) re-binds and `overlay.save` records the fresh index in memory. `EditEntry.file_hash` keeps pinning the intermediate state because `store.file_hash(p)` now hashes overlay bytes. Nothing needs to be copied because nothing needs to be *written* to be readable.
- **`_apply_to_mirror` → `_apply_to_overlay`.** Two-phase discipline preserved: compute every file's new content and verify every `edit.old` before any `write_file`, so `_SpliceMismatch` leaves the overlay untouched. The `file_rename` branch becomes `write_file(new, bytes)` + `delete_file(old)` + `remove(old)` + rebind under the new module path (no `Path.rename`, no `mkdir`).
- **`flatten_batch` diffs the overlay, not a directory.** `BatchResult.root: Path` is deleted; `BatchResult.store` becomes the overlay. `mirror_root.rglob("*")` is replaced by a new `OverlayIndexStore.overlaid_files() -> list[str]` / `deleted_files() -> list[str]` accessor pair (storage may only import `models`; these are pure dict/set views). This is equivalent by construction — a path never written reads through to disk and diffs to zero — and it drops the `STORAGE_DIR`/`LEGACY_STORAGE_DIR` filtering and the `pyproject.toml` copy, both of which existed only to keep the mirror walk honest. `FlattenError` messages and the created/deleted/renamed refusals are unchanged verbatim.
- **`materialize_mirror` is deleted**, along with `work_dir` on `run_batch`/`submit_intents`/`plan_privatize` and the `mkdtemp`/`rmtree` blocks in `cli.py:batch` and `plan_privatize`. It has one caller and one purpose, both gone; keeping it as dead-but-exported code would rot and `report-unused-allowances = true` shows the project's stance on that. It is not in the `refactor` barrel, so no barrel contract changes.
- **`privatize._rewrite_barrel_all_entries`** takes the overlay instead of `mirror_root` and uses `read_file`/`file_exists`/`write_file`. It deliberately does not rebind (it didn't before either) — `flatten_batch` only reads bytes. Its docstring's "Mutating the mirror before flattening" rationale is updated in place.
- `load_src_roots(store.project_root)` now reads the real `pyproject.toml` directly, which is what the mirror was copying it to simulate.

## PR3 — Collapse the fast path

Two additive fields carry the two things the engine currently drops:
- `ExecutedIntent` gains `summary: TransactionSummary | None = None` and `warnings: tuple[str, ...] = ()`, populated from the `Materialized` at `batch.py` L724-731.
- `DroppedIntent` gains `code: str | None = None`, populated from `MaterializeError.code` at the drop site — the exact additive move TASK-125 made for `precondition`, and the mechanism that keeps promote/demote's refusal classes (`export-target`, `protected-public-api`, `rename-refused`) intact.

`submit_intent` then becomes: `result = run_batch([intent], store, policy=ALL_OR_NOTHING, tx_store=tx_store)`; on `BatchAborted` map `dropped[-1]` → `SubmitError(d.code or default_error_code, d.detail, precondition=d.precondition)`; on `ScheduleError` keep `SubmitError("schedule-failed", ...)`; on success return `Materialized(edits=e.edits, file_rename=e.file_rename, summary=e.summary, warnings=list(e.warnings))` rebuilt from `result.executed[0]`. `submit_intents` loses its `len == 1` branch and calls the same engine for every n, returning `Materialized` for n==1 and `BatchResult` otherwise (the return-type discrimination is the caller-facing contract and is preserved).

**How batch-of-one keeps returning the planner's own summary — decision and justification.** Carry it, do not recompute it. `run_batch` is given the caller's REAL `tx_store` for a batch of one, so the planner's `plan()` persists its own transaction exactly as today; the engine forwards that planner-native `TransactionSummary` up through `ExecutedIntent`. Rejected alternatives: (a) synthesize a summary in the engine from the flattened diff — this would set `operation: "batch"` and blank `symbol_id`/`old_name`/`new_name` (flatten_batch's documented convention), breaking the frozen `TransactionSummary` shape and every parity test in `test_app_submit.py::TestSingleIntentParity`; (b) have submit call `flatten_batch` and apply the flattened transaction — same shape break plus a different `tx_id` and lost `warnings`; (c) keep calling the materializer directly "just for n==1" — that *is* the second path, i.e. the thing being deleted.

**Uniformity vs the overlay fold.** The engine will splice + rebind into the throwaway overlay even for a batch of one. This is accepted deliberately rather than special-cased: the splice re-verifies `edit.old` against the very bytes the planner just read, so a `_SpliceMismatch` there is unreachable by construction, and skipping it for "the last intent" is wrong for real batches (flatten needs the final state). The cost is one in-memory splice and one re-bind per submit, on a path that already parses the file. Review lens B is pointed directly at the unreachability claim.

**`check --fix` is unaffected by construction.** It calls `submit_intent` per remedy against the real store with a scratch tx store; each call now builds its own fresh overlay over that same unmutated store, so "every surviving repair is planned against ONE state (the pre-fix tree)" — the property its docstring L33-36 makes load-bearing for the stable `(file, first edit offset, fix_id)` ordering — still holds, and the byte-range conflict model stays in `check_fixes`, not the engine.

**Docs.** PR2 rewrites `batch.py`'s module docstring L31-44 (the mirror paragraph) and PR3 deletes the third bullet of architecture.md's "Walls this makes visible" list and folds the outcome into the batch/refactoring sections, per CLAUDE.md's "fold each remaining item here into them as it lands".

### Risks

- **Real-tree contamination is the catastrophic failure mode.** Under the mirror, `store.project_root` pointed at a temp dir, so every write in the simulation loop was inherently safe. Under the overlay it points at the user's project. The specific landmines verified in the current code: `TransactionStore(mirror.project_root)` (batch.py L678), `_apply_to_mirror`'s `Path.rename`/`write_bytes` (L613-624), and `privatize._rewrite_barrel_all_entries`'s `target.write_bytes()` (L526). Mitigation: explicit `tx_store` parameter, lens A's whole-directory snapshot tests, and a hard rule that nothing in the simulation loop constructs a path from `project_root`.
- **`OverlayIndexStore.compute_file_hash` is a static, disk-based method that looks overlay-aware.** Any planner site missed in PR1 will keep hashing the real file while planning against overlay bytes, producing an `EditEntry` whose `file_hash` pins a state the offsets are not valid for — which the applier will then either reject (visible) or, worse, accept if the file happens to be unchanged (silent, and only wrong inside multi-intent batches). Mitigation: PR1's per-site overlay-mutation proof tests; lens B greps for survivors.
- **`ExtractMethodPlanner`'s `read_text()` → `.decode("utf-8")`** changes decoding from locale/universal-newlines to strict UTF-8 with newlines preserved. `plan()` then does `source.splitlines(keepends=True)` and slices by line, so a CRLF file's behavior could shift. Mitigation: explicit CRLF and non-ASCII fixtures in PR1's proof tests.
- **The mirror contained only indexed files; the overlay reads through to the whole real tree.** A planner that touches a file present on disk but absent from the index used to get `FileNotFoundError` and now succeeds. Arguably a fix, but it is a behavior change in the drop/decline vocabulary. Mitigation: lens B enumerates the affected paths; if any changes a user-visible outcome, it is documented in architecture.md rather than absorbed silently.
- **`flatten_batch`'s file-set derivation changes** from "walk the mirror directory" to "the overlay's written/deleted paths". Equivalent by construction, but the old code also filtered `.pypeeker`/`.semantic-tool` and swept up the copied `pyproject.toml`, and inferred "deleted" from files `materialize_mirror` could not read. Those inference paths disappear. Mitigation: PR2's flatten-equivalence test compares the full `(header, edits)` against the mirror-era expectation.
- **`DroppedIntent.code` must be threaded from `MaterializeError`, or promote/demote silently degrade to `plan-refused`.** The current drop site (batch.py L710-716) reads `precondition` but not `code`. This is a one-line omission with a JSON-visible consequence. Mitigation: PR3 proof tests assert the exact code per refusal class.
- **Batch-of-one now splices and re-binds into a throwaway overlay.** The claim that `_SpliceMismatch` is unreachable there (the planner read the bytes it anchored to) is load-bearing: if false, a currently-succeeding `rename` becomes a `plan-refused`. Mitigation: lens B is pointed at it explicitly, with self-overlapping edits and `_build_edits`' `(file,start,end)` dedup as the named counter-example candidates.
- **`check --fix` builds one overlay per remedy** (it loops `submit_intent`). That preserves its "planned against one pre-fix state" property but adds N overlay constructions per run. Cheap (the overlay is two empty dicts and two empty sets until written), but worth confirming no per-call `list_indexed_files()` sweep was introduced.
- **Scope creep into the other two walls.** The overlay's `write_file`/`delete_file` tombstones make file birth/death *look* one refactor away, and `MAX_PLAN_ATTEMPTS_PER_INTENT = 1` makes a fixpoint loop look tempting. Both are separate walls in architecture.md's list and are explicitly out of scope; `flatten_batch`'s created/deleted `FlattenError` refusals stay exactly as they are.

## Plan B — fixpoint-remedies

### ITEM B — Bounded fixpoint scheduling for cascading check --fix remedies (opt-in --fix-until-clean, mirror-simulated, one transaction)

**Scope:** L — roughly 250-400 lines of source across four files plus ~13 new tests, with the risk concentrated in one judgment-heavy module (`app/check_fixes.py`). Split into two PRs: PR1 = Stages 1-2 (behavior-preserving extraction of `apply_edits_to_mirror` / `flatten_tree`, four barrel exports, `SIMULATION_UNSAFE_RULES`) which ships green on its own with zero behavior change and can be reviewed purely as a refactor; PR2 = Stages 3-4 (the loop, the CLI flags, the additive report keys, the docs). Splitting matters here because PR1's correctness argument is "no test changed and no behavior changed", which is much easier to verify in isolation than folded into a feature diff.

### Problem
`check --fix` plans the remedies of the findings it sees once and applies them as one transaction. But repairs reveal repairs: deleting a dead private symbol can make its only import unused, and removing one import can leave another unused. Today the user must notice this and re-run the command, and there is no signal in the report that a second pass would find more. I verified the gap on a live throwaway project: with `unused-imports` + `unused-public-symbol --also-private`, a module whose only consumer of `import os` is a dead `_dead()` reports exactly one auto-fixable finding; after that fix lands, a second run finds `import os` unused. A second, independent source of the same problem already exists in-band: a repair skipped under `skipped_conflicts` because its bytes overlapped a winning repair is simply abandoned for that run, even though the winner's edits have made it plannable again. A bounded fixpoint turns "run it until it stops changing things" from a human loop into one command, without loosening the safety of a command that writes bytes by default.

### Current state (verified)
Single pass, and deliberately so. `app/check_fixes.py:apply_check_fixes` loops once over the `violations` it is handed, filters with `auto_fixable` (remedy present and `Confidence.DECLARED`), submits each remedy through `app/submit.py:submit_intent` against the REAL `IndexStore` with a throwaway `TransactionStore` from `_scratch_transactions()`, sorts survivors by `_order` = `(first edit file, first edit start, remedy.intent_id)`, drops byte-overlapping repairs into `skipped_conflicts`, writes ONE `TransactionHeader(operation="check-fix")` via `transaction_store.save`, and — unless `plan_only` — applies it through `refactor/applier.py:TransactionApplier.apply` and recomputes `residual = engine.run()`. `refactor/batch.py`'s module docstring states the constraint outright: "Iteration is a single pass over the schedule — no fixpoint loop", backed by `MAX_PLAN_ATTEMPTS_PER_INTENT = 1`. architecture.md's "Walls this makes visible" list names it as wall 2: "Scheduling is single-pass — cascading remedies (remove import → symbol becomes unused → delete symbol) need a fixpoint or a re-run."

The report is frozen and asserted exactly. `cli.py:_apply_check_fixes` emits `{fixes, skipped_conflicts, declined, residual_violations, tx_id}`, plus `applied: true` and `files_modified`/`files_reindexed`/`files_reindex_failed` only when an apply happened. `tests/test_check_fix.py::TestCheckFixCli::test_clean_project_fix_is_a_no_op` asserts `report == {...}` by exact dict equality — any unconditional new key fails it. `test_all_three_fixes_apply_in_one_transaction` pins the ordered `fix_id` list and `applied is True`; `test_overlapping_fixes_skipped_deterministically` pins that the tuplify inside a deleted `_dead` lands in `skipped_conflicts` (not `declined`), which is exactly the bucketing a naive serialize-everything loop would break.

The simulation substrate already exists and is proven, but is not reachable from `app`. `refactor/batch.py:materialize_mirror` copies every indexed file's bytes plus `pyproject.toml` into a temp dir and re-saves each `FileIndex` into a fresh `IndexStore` rooted there (reading through `store.read_file` when the store offers it, so an overlay feeds it); `_apply_to_mirror` splices one `Materialized`'s edits bottom-to-top and re-binds touched files via `refactor/simulate.py:rebind_source`; `flatten_batch` diffs the mirror against the real tree into ONE transaction with `_trim_common_lines`, hash-anchored to the real plan-time files. `refactor/privatize.py:plan_privatize` is the working precedent for mirror → flatten → one transaction (temp dir via `mkdtemp`, `shutil.rmtree` in a `finally`). None of `materialize_mirror`, `_apply_to_mirror`, `flatten_batch`'s inner diff, or `rebind_source` is exported from `refactor/__init__.py`'s curated `__all__`, so `app` cannot reach them without violating the gated `barrel-only` rule.

Planners read bytes off disk, not through the store: `delete.py:144`, `imports_ops.py:212,452`, `literals.py:265`, `docstring_ops.py:152`, `extract.py:173,235`, `inline.py:185`, `planner.py:472,554,609`, `preconditions.py:177,746,772`, `dataflow.py:122` all do `self._index_store.project_root / path`. That is precisely why `batch.py`'s docstring calls the temp-dir mirror "v1" and the overlay "the zero-copy future" — `OverlayIndexStore` (storage/overlay.py) is fully implemented but its file-bytes layer would be bypassed by every planner today. This is the ITEM A dependency.

`CheckEngine` is store-agnostic: `check/engine.py:CheckEngine.run` only calls `store.list_indexed_files()` / `store.load()`, and `check/context.py:CheckContext` only holds the store plus indexes and builds resolver/tree lazily from them. So re-running rules over a mirror store works with no engine change. I confirmed this with a live probe: mirror created once, iteration 1 found `unused-symbol:delete:mod:_dead` (and no import finding), iteration 2 found `unused-imports:remove:mod:os` (revealed by iteration 1), iteration 3 was quiescent, `flatten_batch` over a synthetic `BatchResult(executed=(), root=mirror_dir, ...)` produced one `delete` edit spanning bytes 0..48 of `src/mod.py`, and the real tree was untouched throughout.

Two mirror-fidelity hazards are real, not hypothetical. `check/builtin/born_private.py:182` does `baseline_path(context.store.project_root)` and writes a symbol baseline — run against a mirror it would read a nonexistent baseline, self-seed from the mirror's surface, and report nothing. `check/engine.py:_load_plugins` inserts `store.project_root` on `sys.path` and imports configured plugin modules; a top-level `lint_rules.py` is not an indexed file, so `materialize_mirror` never copies it (the import only survives because `sys.modules` already caches it from the pre-loop real-store run).

Layering as enforced by `[tool.pypeeker.import-boundaries]`: `app = ["check", "intents", "models", "refactor", "storage"]`, `strict = true`, `report-unused-allowances = true`; `check` has no `refactor` allowance and must keep none. Self-lint is currently clean (`uv run pypeeker check --no-refresh` → exit 0, 11 hidden HEURISTIC findings). `materialize_mirror` is among those 11 (`over-exposed-module-symbol`, heuristic because `batch.py` uses `getattr`); barrel-exporting it removes the finding rather than adding one, since `_over_exposed_module_symbol` exempts barrel-re-exported canonical ids.

### Design
**Opt-in, not default.** A new flag `--fix-until-clean` (with `--fix-max-iterations N`, default 10) turns the fixpoint on; plain `check --fix` keeps today's exact single pass and today's exact report bytes. Three reasons, in order of weight. (1) The frozen report is asserted by exact dict equality in `test_clean_project_fix_is_a_no_op`, so an unconditional key is a break, not an additive extension; architecture.md's Output contract permits "new optional keys", and a key that exists only when the caller opted into the behavior it describes is the strictest reading of optional. (2) Apply-by-default (TASK-126) means the command writes bytes with no confirmation step; a fixpoint widens the blast radius from "the repairs for findings you were just shown" to "repairs for findings that do not exist yet", including deleting private helpers the user never saw named. That is a policy change and must be requested. (3) Single-pass planning against one state is what makes the `(file, start, fix_id)` ordering key meaningful and is documented as load-bearing in both `check_fixes.py` and `batch.py`; keeping it as the default costs nothing and preserves the reference semantics the loop is defined in terms of.

**The loop is N repetitions of today's pass, not a new algorithm.** Extract the existing body of `apply_check_fixes` into `_plan_pass(store, tx_store, violations) -> (fixes, skipped_conflicts, declined, kept_materialized)` — submit, sort by `_order`, de-conflict on byte ranges. Both paths call it. `apply_check_fixes` gains `max_iterations: int = 1`; at `1` it takes literally the pre-change control flow (real store, no mirror, no temp dir, no flatten), so "the default is byte-identical" is structurally enforced rather than promised. At `> 1` it creates ONE mirror via `materialize_mirror` (once for the whole loop, then mutated in place — this is why iterating is cheap even on the copy substrate), and per iteration: run `CheckEngine(mirror, loop_config).run()`, call `_plan_pass` against the mirror, splice the kept edit set into the mirror as one batch and re-bind touched files, then decide whether to continue.

Applying the kept set as *one* splice batch (rather than one repair at a time) is what preserves the frozen conflict semantics. Serializing repairs individually would make the loser of a byte overlap re-plan against post-winner bytes and decline `stale-index`/`text-mismatch` — the wrong bucket, and exactly the failure `check_fixes.py`'s docstring already says `run_batch` would produce. Keeping the pass intact means iteration 1's `fixes`/`skipped_conflicts`/`declined` are identical to what plain `--fix` produces, and a conflict-skipped repair simply gets a fresh, legitimate chance next iteration — a second, independent source of progress beyond rule cascades.

**Loop rule set vs residual rule set.** The per-iteration engine run uses `dataclasses.replace(config, rules=tuple(r for r in config.rules if r not in SIMULATION_UNSAFE_RULES))`, a new exported frozenset in `check` currently holding `born-private` only, documented as "rules that persist or self-seed state keyed to the store's project root, and therefore report differently against a simulated tree". The full configured rule set is kept otherwise (not narrowed to remedy-bearing rules), so cascades that cross rule families are caught. The post-apply `residual = engine.run()` stays exactly as today: the original engine, the original config including `born-private`, against the REAL store.

**Transaction discipline: still ONE transaction.** At loop exit the final mirror tree is diffed against the real tree into a single `check-fix` transaction and applied once — the `plan_privatize` / `plan-batch` shape. Chained per-iteration transactions are rejected: N transactions means N rollbacks in reverse order, a mid-chain apply failure leaves the tree in an intermediate state no single command undoes, and the frozen scalar `tx_id` would have to become a list. One transaction also gives the loop its strongest safety property — the real tree is written exactly once, at the end, after the entire cascade has been simulated. Cost, stated honestly: the flattened edits are line-trimmed whole-region splices rather than per-repair edits (my probe produced one 0..48 `delete` where the default path would produce two precise edits), so `transactions show` is coarser under the flag. That is the same trade `batch` and `privatize` already make, and it only applies under the flag.

Mechanically this needs `flatten_batch`'s diff half factored out: `flatten_tree(mirror_root, real_store, *, operation) -> (TransactionHeader, list[EditEntry])`, with `flatten_batch` reduced to the file-rename wall plus a delegation. `flatten_tree`'s created/deleted-file walls are inherited: none of the five remedy planners can create or delete a file today (`delete-symbol` empties a file's contents, it does not unlink it — the frozen overlap test asserts the file becomes `""`), but a `FlattenError` must be caught and reported through the existing flat error envelope, never allowed to escape as a traceback.

**Termination and determinism.** There is no honest monotonicity argument and the plan does not claim one: a repair can strictly increase the finding count (removing one import can reveal several unused imports; `rewrite-star-import` and `rename-docstring-param` can add bytes), so neither finding count nor byte count is a decreasing measure. Termination rests on four guards, all reported:

- *Quiescence* — an iteration keeps zero repairs. `stop_reason: "quiescent"`, `quiescent: true`.
- *Iteration cap* — `--fix-max-iterations` (default 10, must be >= 2 under the flag). `stop_reason: "max-iterations"`, `quiescent: false`.
- *Repeated fix* — a `fix_id` already applied earlier in this run is proposed again, meaning the repair did not stick. `stop_reason: "repeated-fix"`, `quiescent: false`.
- *Tree cycle* — SHA-256 over the sorted `(path, sha256(bytes))` of the mirror after each iteration; a repeat means an A→B→A oscillation. `stop_reason: "cycle"`, `quiescent: false`. This is the guard that actually bounds the loop in the general case; the cap is the backstop.

Determinism follows from each iteration being a pure function of the previous mirror tree: `CheckEngine.run` sorts violations, `_plan_pass` sorts by `(file, start, fix_id)`, mirror splices are deterministic. The cross-iteration report order is `(iteration, file, start, fix_id)`. The temp mirror path must never reach the report — precondition failure messages use relative paths (`AnchorFileExists`: `f"{self.file_path} no longer exists"`, `AnchorIndexFresh`: `f"{self.file_path} changed since it was indexed…"`), which the review must re-verify for every reachable refusal.

**Report extension (flag-only, additive).** Under `--fix-until-clean` the report keeps every existing key with its existing meaning and gains `iterations` (per-iteration `{iteration, fixes, skipped_conflicts, declined}` counts), `iterations_run`, `quiescent`, and `stop_reason` (always present, so non-quiescence is never silent). `fixes` remains the flat ordered union of every applied repair, each entry gaining `"iteration": n`. `skipped_conflicts` and `declined` are deduped by `fix_id` keeping the LAST verdict, so a repair skipped in iteration 1 and applied in iteration 2 appears only under `fixes` and an N-iteration run does not emit N copies of the same decline. `applied` stays a bool, `tx_id` stays a scalar, `fixes` is never renamed. Exit code semantics are unchanged: non-zero iff shown residual findings remain.

**Safety posture under apply-by-default.** The real `IndexStore` and working tree are read-only for the entire loop; the only write is the single applier call at the end. Every iteration re-validates through the real precondition machinery — each remedy is re-planned by its registered planner against the mirror, so `AnchorFileExists` / `AnchorIndexFresh` / `AnchorTextMatches` / `DeletableScope` / `ImportLineSurgerySafe` are evaluated pointwise against simulated bytes, not once at t=0. The per-iteration re-bind is load-bearing and self-checking: if it were forgotten, `AnchorIndexFresh` would decline every subsequent repair `stale-index` rather than let a stale-offset edit through — a fail-closed canary worth asserting in a test. The final transaction is hash-anchored to the real plan-time files, so an external edit during the loop is caught by `TransactionApplier._verify_hashes` pre-flight, leaving the transaction PENDING and the tree untouched; no new refusal code is introduced, an apply failure surfaces through the existing `apply-failed` envelope with `tx_id`. `--plan` composes: the flattened transaction is written PENDING, nothing is touched, `residual` is the unmodified input set. The mirror directory is removed on every exit path via `try/finally` + `shutil.rmtree(ignore_errors=True)`, and per-remedy planner transactions continue to go to a throwaway store so only the combined `check-fix` transaction reaches the project. The mirror's `.pypeeker` directory is already excluded from the flatten walk by `flatten_batch`'s `STORAGE_DIR`/`LEGACY_STORAGE_DIR` filter, which `flatten_tree` must preserve.

**Layering.** The loop lives in `app/check_fixes.py` — it is the composition of `check` (re-run rules) and `refactor` (simulate, flatten, apply), which is exactly what `app` exists for; `check` gains no `refactor` allowance and `intents` stays on `models`/`query`/`storage`. The three substrate helpers (`materialize_mirror`, `apply_edits_to_mirror`, `flatten_tree`) plus `rebind_source` must be added to `refactor/__init__.py`'s `__all__` to satisfy `barrel-only`; this also clears the existing heuristic `over-exposed-module-symbol` finding on `materialize_mirror` rather than adding one.

**ITEM A interaction, and preferred order.** The loop is written against a narrow substrate seam — create, apply-edits, snapshot-hash, diff-against-real — with a mirror-backed implementation now. If ITEM A (planners reading bytes through the store) lands first, the same loop swaps `materialize_mirror` for an `OverlayIndexStore` with no change to its shape: only the constructor and the `diff_against_real` implementation differ, and the O(indexed bytes) copy disappears. **Preference: ITEM B first on the mirror.** The mirror is the substrate `batch` and `privatize` already run on in production, it needs no planner changes, and shipping the fixpoint on it produces exactly the multi-iteration test suite that will later prove the overlay swap is behavior-preserving — a much better validation story than landing the substrate change first with only single-pass tests to protect it. The copy cost is paid once per flagged run, not per iteration, which keeps mirror-first cheap enough that it is not a stopgap under duress.

### Acceptance criteria

- `check --fix` without the new flag produces byte-identical JSON to the pre-change build on every path (no fixes, some fixes, all declined, conflicts, `--plan`, apply failure), and takes a control flow with no mirror, no temp directory, and no flatten.
- `check --fix --fix-until-clean` reaches quiescence on a cascade that plain `--fix` only half-repairs, applying both the revealed repair and the conflict-skipped repair, in one command.
- The whole run lands as exactly ONE `check-fix` transaction; a single `rollback <tx_id>` restores the pre-loop bytes byte-for-byte, and `transactions show <tx_id>` reports `operation: check-fix`.
- The real working tree is byte-identical from command start until the single apply at loop exit; every iteration's planning and splicing happens on the mirror, and the mirror directory is removed on every exit path.
- Every remedy is re-validated by its registered planner against the state the previous iteration produced — no repair is applied on offsets computed against an older tree — and the per-iteration re-bind is fail-closed (absent it, repairs decline `stale-index` rather than mis-apply).
- The loop always terminates and always reports why: `stop_reason` is one of `quiescent` / `max-iterations` / `repeated-fix` / `cycle`, is present on every flagged run, and `quiescent` is `false` for the last three.
- The flagged report is a strict superset of the frozen one: `fixes` / `skipped_conflicts` / `declined` / `residual_violations` / `tx_id` / `applied` keep their names, types, and meanings; `applied` stays boolean; `tx_id` stays scalar; new keys appear only under the flag.
- `--fix-until-clean --plan` writes the flattened transaction PENDING, touches no file, and a later `apply <tx_id>` produces exactly the bytes the applied run would have.
- `residual_violations` is still computed by the original engine with the original config against the real store after apply, including rules excluded from the loop's mirror runs.
- Layering holds: `check` gains no `refactor` import, `intents` stays on `models`/`query`/`storage`, every new cross-package import resolves through a barrel `__all__`, and `import-boundaries` strict mode plus `report-unused-allowances` stay clean.
- No file under `tests/` is edited — only added; the three-command gate (pytest, ruff, index+check with no baseline) is green.
- architecture.md's 'Walls this makes visible' item 2 (single-pass scheduling) is struck and its landed behavior folded into the Refactoring Model and Output contract sections; `refactor/batch.py`'s 'no fixpoint loop' docstring sentence is corrected to scope the claim to the batch scheduler.

### Risks

- Two divergent fix algorithms. If the `max_iterations=1` path and the loop path drift, the flag stops being a superset of the default and the frozen tests only protect one of them. Mitigated by both paths calling the same extracted `_plan_pass`, and by the review lens that reads the branch rather than trusting tests.
- Conflict-bucket regression. Applying kept repairs one at a time instead of as one splice batch would convert `skipped_conflicts` entries into `declined` entries — the exact wrong-bucket failure `check_fixes.py`'s docstring already warns about for `run_batch`. The frozen overlap test catches it only for iteration 1; iterations 2+ have no frozen guard, hence the dedicated new test.
- Coarser transaction edits under the flag. `flatten_tree` emits line-trimmed whole-region splices (my probe: one 0..48 `delete` where the default path emits two precise edits), so `transactions show` is less legible and a driver that inspected per-fix edits sees fewer, larger ones. Accepted: same trade `batch` and `privatize` already make, and flag-gated.
- Mirror infidelity changing rule verdicts. The mirror holds only indexed files plus `pyproject.toml`. Plugin rule modules outside `src` are absent, and the loop's engine run currently survives only because `sys.modules` caches them from the pre-loop real-store run — a fragile dependency that a future lazily-loaded plugin would break.
- Stateful-rule exclusion is a manual list. `SIMULATION_UNSAFE_RULES` must grow whenever a rule starts persisting state; a rule that writes under `context.store.project_root` and is NOT in the list will silently report differently on the mirror, changing which repairs the loop plans. The audit-every-builtin-for-writes step in lens 3 is the only systematic defense.
- Non-termination in the general case. There is no monotonicity argument; the cap and the tree-hash cycle detector are the only bounds. A pathological rule set could exhaust the cap on every run, making `--fix-until-clean` misleading in name — hence `stop_reason` being mandatory rather than optional.
- Blast radius under apply-by-default. Even opt-in, one command can now delete code the user never saw flagged (a private helper orphaned by an earlier deletion). `--plan` is the mitigation and must be documented as the recommended first invocation of the flag.
- Copy cost on large projects. `materialize_mirror` copies every indexed file once per flagged run. Bounded and paid once (not per iteration), and eliminated entirely by ITEM A, but it makes `--fix-until-clean` measurably heavier than `--fix` on a big tree.
- Inherited flatten walls. A future remedy planner that creates or deletes a file turns the whole flagged run into a `FlattenError`; it must be reported through the flat error envelope, and the underlying wall is ITEM-A-adjacent work (`flatten_batch` refusing file birth/death is architecture.md's wall 1, still open).

### Problem

### Design
**1. The second pair: a `type-annotation` trait, not a `purity` trait.** Reject the purity pair for the four reasons in current_state (different anchor, different depth, different policy, different verdict type — and its derivation is already shared through `analysis.purity`). Migrate instead the fact both `prefer_tuple` and `InferredListBinding` derive from `Symbol.type_annotation`.

New module `src/pypeeker/analysis/type_annotation.py`:
- `TYPE_ANNOTATION = "type-annotation"`.
- `@register_trait(TYPE_ANNOTATION) def _type_annotation(file_index: FileIndex, symbol_id: str) -> Trait` — finds the symbol in `file_index.symbols`; returns `Trait(value=<ann.raw or None>, confidence=<ann.confidence, or Confidence.UNKNOWN when there is no annotation / no such symbol>, provenance=...)`. Never raises on a missing symbol: an absent symbol is `value=None, confidence=UNKNOWN`, which makes every downstream predicate false. Signature is exactly the existing `TraitProvider` shape — this is the point: the second pair *validates* the signature architecture.md called provisional rather than forcing a generalization.
- `value` is a bare `str | None` (the raw annotation text), deliberately not a one-field dataclass: `VariableMutation` is a record because it carries three independent booleans, whereas here the value is one scalar and the second dimension (confidence) already has a home on `Trait`. The module docstring states what `value` is for this trait name, per the `Trait.value: Any` contract.
- `def is_inferred_list(trait: Trait) -> bool: return trait.value == "list" and trait.confidence is Confidence.INFERRED` — the one place the composite predicate is written, mirroring how `VariableMutation.is_mutated` is a convenience for the one consumer that wants a union. Two real src consumers (the rule and the precondition), so the "no exported provider without a real consumer" gate is satisfied by consumption, not by the barrel exemption alone.

This is the honest migration of `TypeAnnotation.confidence` onto the Trait envelope: the model field stays where the binder writes it, and the *consumer-side interpretation* — value-plus-confidence read as one fact — moves into `Trait`. It also leaves two further consumers (`unused_return_value.py:119`, `resolve.py:220`) able to read the same trait later without a new provider.

**2. Consumer cutover, byte-identical.**
- `check/rules.py prefer_tuple`: replace lines 405-407 with a `get_trait_provider(TYPE_ANNOTATION)` call guarded by the same `assert ... is not None` idiom already used for `VARIABLE_MUTATION`, and `is_inferred_list(trait)`. Reorder the candidate loop so the cheap `scope_kind` test runs *before* the trait call — behavior-identical (both are pure filters; `candidates` still fills in `file_index.symbols` order) and it keeps the added per-symbol scan off every module-level variable. The `Violation` constructed at rules.py:436-452 keeps its default `confidence` (DECLARED) — **the trait's confidence must not be propagated to the finding.**
- `refactor/preconditions.py InferredListBinding`: constructor becomes `(name: str, symbol: Symbol, index: FileIndex)`, mirroring `NotReassigned(symbol, index)`; `evaluate` derives `symbol_id` from `symbol.symbol_id`, reads the trait through the registry, and returns the identical `_fail(f"'{self.var_name}' is no longer bound to an inferred list literal")`. `name = "inferred-list-binding"` and `slug = "text-mismatch"` are untouched. `refactor/literals.py:342` updates its one construction site (`state.symbol` and `index_fresh.index` are both already in scope).
- Both consumers reach the new names through the `pypeeker.analysis` barrel; `analysis/__init__.py` gains `TYPE_ANNOTATION` and `is_inferred_list` to `__all__` (and imports the module so the provider self-registers, exactly as `variable_mutation` does).

**3. Which confidence computations become traits — the decision rule.** A confidence computation is promoted to a registered trait provider only when **both** hold:
  (a) **Cross-boundary**: the fact is derived independently in `check` *and* in `refactor` — a rule quantifies it and a precondition/planner verifies it. Sharing among several `check` rules is already solved by a private helper in `check/rules.py`; adding a registry entry there buys no de-duplication and costs a publicly overridable seam (`register_trait` has no builtin guard — a plugin re-registering the name changes behavior).
  (b) **Anchor-shaped**: it is derivable from one already-loaded `FileIndex` plus one `symbol_id`. A fact needing the store, resolver, or a project-wide sweep does not fit `TraitProvider`; inventing a second provider shape for a fact with no cross-boundary consumer is speculative generality (architecture.md already licenses a second shape *when a trait needs it*, which is not now).
Applying it to the inventory:
| Computation | Verdict | Reason |
|---|---|---|
| `TypeAnnotation.confidence` (prefer_tuple / InferredListBinding) | **Migrate now** | (a) and (b) both hold; derivation is literally duplicated across the boundary |
| `_dynamic_access_confidence` | Stay local, **strongest future candidate** | Fails (b): needs a project-wide `_dynamic_access_modules` sweep. Its value already crosses to `refactor.privatize` as a string via `demotion.demote_entry`; making privatize *re-derive* it would also change behavior for explicitly-passed symbol ids. Revisit if/when a project-scoped provider shape is justified on its own merits |
| `_impurity_confidence` | Stay local | Fails (a) — 3 consumers, all in `check` — and (b): takes `Observations`. The underlying purity analysis is already shared via `analysis.purity` |
| `star_imports` file-confidence, `unused_imports`, `import_time_side_effects` | Stay local | Single-rule, single-use |
| `Symbol.import_confidence` readers | Stay local | 3 consumers, all in `check`; a plain model-field read, not a derivation |
| `Symbol.visibility_confidence` | **Do not migrate; record as dead** | Zero readers in `src/`. A provider with no consumer is forbidden by the `unused-public-symbol` gate and by the mechanism's own rule |
Rejected alternative: "any computation with ≥2 consumers becomes a trait." That would promote `_impurity_confidence` and `_dynamic_access_confidence` on a count, turning `analysis/` into a dumping ground of check-internal helpers, exporting overridable seams for facts no refactor ever verifies, and inventing a second provider signature for the first one that doesn't fit.

**4. `Trait.provenance` convention.** Standardize the shape already set by `variable_mutation`, as a documented convention on `Trait.provenance`'s docstring, not as code: `"<provider module dotted path>: <the facts read> for '<anchor id>' in <file path>"` — three parts, producer / evidence / anchor, human-readable prose. Explicitly **not** standardized: no structured type, no parser, no machine format, no schema version. And one hard guardrail, stated in the docstring and architecture.md: **provenance is never serialized into CLI JSON, a `Violation.message`, or a refusal `reason`** — the moment it appears in output it becomes a frozen contract, which is exactly the over-engineering this convention is meant to avoid. Conformance is asserted by one test that reaches `traits._REGISTRY` directly (a *private* accessor, deliberately: a public `registered_trait_names()` whose only consumer is `tests/` would be flagged by the gated `unused-public-symbol` rule, which indexes `src` only).

**5. Docs.** Update architecture.md's "Traits (TASK-127)" paragraph (it currently says "This is one migrated pair, not a completed migration") to describe two pairs and the provenance convention; update structural item 6 (lines 410-418) to record `TypeAnnotation.confidence` as migrated and to carry the inventory table plus the promotion rule, so the remaining two fields have stated verdicts rather than an open TODO; record the purity-pair rejection and its four reasons so it is not re-proposed. Track the work as a Backlog.md task via the `backlog` CLI (never by editing task files).

### Risks

- **Confidence leak into the finding (highest-severity, one-line).** Wiring `Violation(confidence=trait.confidence)` in prefer_tuple would set INFERRED, which silently disables its autofix (`app/check_fixes.py:110` requires DECLARED) and appends ' [inferred]' to the ruff-style output line. Mitigated by an explicit stage-3 instruction, Lens A's first hunting ground, and the existing test_check_fix.py fix_id assertions — but note no current test asserts prefer-tuple's finding *confidence* directly, so the stage-1 oracle work should be extended if a reviewer wants that pinned too.
- **Cost regression in prefer_tuple.** The provider looks the symbol up by scanning `file_index.symbols`, so a naive cutover is O(candidates x symbols) per file on top of variable_mutation's existing O(candidates x references). Mitigated by moving the cheap `scope_kind` filter ahead of the trait call; if the self-lint's `index src && check` wall time regresses noticeably, the fallback is to keep prefer_tuple's `kind == VARIABLE` pre-filter first as well. prefer-tuple is not in the gated rule set, so this affects consumer projects rather than CI.
- **Barrel/`__all__` coupling trap.** Adding names to `analysis.__all__` retroactively makes deep imports of those names illegal under `barrel-only` (a gated rule). The inverse risk is subtler: adding an unrelated name (e.g. `PurityPolicy`) to `__all__` while editing the barrel would immediately break the legal deep import at `check/rules.py:28`. The barrel edit must be strictly additive and limited to the two new names.
- **Scope creep into the rejected migrations.** An implementer or reviewer may 'helpfully' also migrate `_impurity_confidence` or `_dynamic_access_confidence`. Both fail the promotion rule; `_dynamic_access_confidence` in particular would need a project-scoped provider shape and, if privatize were made to re-derive it instead of trusting `demote_entry`'s string, would change `privatize` behavior for explicitly-passed symbol ids. Stage 7 rejects such findings by policy.
- **The 'same rule twice' objection.** Both proven pairs quantify from `prefer_tuple`. The mitigation is substantive rather than cosmetic — the second pair's verifying side is a different precondition in a different planner, the fact is derived from a different part of the model (type annotation vs references), and it is the first pair where the ∀ and the pointwise check guard the *same* remedy end-to-end — but the plan should say so out loud in architecture.md so a future reader does not read it as double-counting.
- **Provenance convention over-reach.** Formalizing provenance is one docstring away from becoming a parsed format. The guardrail (never serialized into JSON, messages, or refusal reasons) is the entire defense; if a later change surfaces provenance in output, it becomes a frozen contract by accident.

### ITEM D — File birth/death in the batch engine + EdgeAnchor, unlocking move-symbol

### Design
Four decisions, then the PR split.

**1. Transaction model: two new entry types, self-contained, with a header version.**

Add `EditOp.CREATE_FILE = "create_file"` and `EditOp.DELETE_FILE = "delete_file"`, plus:

- `FileCreateEntry(path, content, content_hash, op=CREATE_FILE)` — `content` is the full text to write (the entry is self-contained, so rollback and `transactions show` need no other source). There is deliberately **no `file_hash`**: the pre-image of a creation is *absence*, and absence is what pre-flight verifies. `content_hash` is the SHA-256 of `content`, used only by rollback, to refuse deleting a file someone edited after apply — the exact parity of `applier.py:196-201`'s restored-hash check.
- `FileDeleteEntry(path, content, file_hash, op=DELETE_FILE)` — `content` is the full pre-image (rollback restores it), `file_hash` keeps its existing meaning and is verified at pre-flight.

The two are inverses: rollback of a create is a guarded delete, rollback of a delete is a guarded create. *Rejected alternative*: expressing creation as an INSERT `EditEntry` over an empty file. Rejected because `_verify_hashes` (`applier.py:274`) demands the file exist, rollback of an INSERT splices text rather than removing the file, and a whole-file INSERT gives `flatten_batch` no way to distinguish "born" from "emptied then filled".

**Versioning (the storage-doc question).** Yes, and on the header, not per line. Add `TransactionHeader.version: int = 1` — additive with a default, so every transaction already on disk reads as version 1 with no migration. `TransactionStore.save` writes `version = 2` **only** when the transaction actually contains a create/delete entry; `load` refuses a header version it does not understand with a clean, machine-coded error instead of the current `TypeError` path. Replace `load`'s single `if op == rename_file / else` with an explicit op→type table plus an unknown-op refusal, so a forward-format file never silently coerces into a malformed `EditEntry`.

`LoadedTransaction` becomes a frozen dataclass (`header`, `edits`, `file_rename`, `creates`, `deletes`) and all seven destructuring sites are updated. *Rationale*: a positional tuple that grows a fourth and fifth element is the shape that rots; the tuple is purely internal (no JSON payload depends on its arity), so this is not a frozen-contract break.

**Applier discipline** — the existing two phases become stage/commit over three resource kinds, ordered so any failure is restorable:
- *Pre-flight* (`_verify_hashes`): every edited/deleted file exists and hash-matches; every created path **does not exist** (refusing with the standard `ApplyError` envelope). This is what makes the failure handler's asymmetric restore safe.
- *Stage*: write edit temps as today; write each creation's content to `path + ".tmp"` (never the real path, and `mkdir(parents=True)` for its directory); buffer each deletion's bytes into `backup_contents`.
- *Commit*: swap edit temps, swap create temps (recording each in a `created` list), unlink deletions, then the rename (unchanged, still at most one).
- *Restore on failure*: rewrite swapped edits from backups, rewrite deleted files from backups, **unlink created files** — the one asymmetric case, safe only because pre-flight proved they did not pre-exist — reverse the rename, clean temps, mark FAILED. FAILED stays terminal.
- *Re-index*: created files bind and save; deleted files get `IndexStore.remove(path)` — closing the ghost-entry hole at `applier.py:415-416`.
- *Rollback*: verify-everything-before-writing (existing discipline). A create rolls back only if the file still hashes to `content_hash`; a delete rolls back only if its path is now free (parity with the rename check at `applier.py:209-213`).

**Output shapes**: additive only. The applier result gains `files_created`/`files_deleted`; `_finish_mutation`'s copy list (`cli.py:562`) gains those two keys; `transactions show` gains `creates`/`deletes` arrays; `transactions list` counts them in `edit_count`. `TransactionSummary`'s field set is untouched.

**2. Teaching `flatten_batch` and the mirror loop.**

`Effect` gains `files_created: frozenset[str]` and `files_deleted: frozenset[str]`, with `then()` composition defined and tested as a table: create→delete cancels both; delete→create nets to a *write* of an existing path; create→write stays a create; create→rename carries the creation to the new path (`_preimage_file` must learn about creations, since it is exact-match today). `Materialized` gains `files_created`/`files_deleted` lists so a planner can declare births/deaths.

`_apply_to_mirror` keeps its two-phase promise ("a `_SpliceMismatch` leaves the mirror exactly as it was"): compute *all* new byte content — including creations — before writing anything, then write creations, then edits, then unlink deletions, then rebind. Deleted paths drop out of the rebind list and get `mirror.remove(path)`; created paths join it. The `FileNotFoundError` escape at `batch.py:611` is closed by making creation explicit rather than inferring it from an edit against a missing file — an edit against a missing file stays a bug and now surfaces as a drop with a machine-readable reason, not a traceback.

`schedule` gains two rules: a file-level analogue of Rule 1 (an intent reading a file another intent deletes runs first) and a new hard conflict — two intents creating the same path have no resolving order, so the later-submitted one drops with `CONFLICT_DROPPED`, mirroring `_shared_written_symbol`'s determinism guarantee.

`flatten_batch` then emits, from the mirror-vs-real diff: shared paths → `EditEntry` (unchanged, including the `_trim_common_lines` shrink); mirror-only → `FileCreateEntry`; real-indexed-but-mirror-missing → `FileDeleteEntry`. **Ordering inside the flattened transaction is a non-question**: the flatten is a *diff*, not a replay, so every entry names a distinct path and the applier's phase order is the only order. A path deleted *and* re-created within one batch appears in both trees and collapses to an ordinary edit — which must be tested, because it is the case that silently distinguishes a diff from a replay.

**Authorization rule**: a mirror-only file is flattened as a creation **only if some executed intent's effect declared it in `files_created`**. An unexplained mirror-only file keeps raising `FlattenError` — the mirror substrate copies only files that exist in the real tree (`materialize_mirror`, `batch.py:496`), so an unclaimed newborn means the substrate leaked, not that a refactoring happened. Deletions are authorized symmetrically. This preserves today's conservatism exactly where it is load-bearing while lifting it where an intent takes responsibility. Executed *file renames* keep raising `FlattenError` — out of scope, and the corresponding test stays frozen.

**3. `EdgeAnchor`, with move-symbol as its first real consumer.**

`EdgeAnchor(source_id: str, target_id: str, kind: str)` — frozen and hashable like its siblings; `kind` starts as the single value `"import"` (no unconsumed vocabulary). `Anchor` becomes the three-way union. Remap semantics: both endpoints follow `Effect.remap_id`; if either is deleted the edge is orphaned. It reuses `OrphanReason.ANCHOR_DELETED` and names the dead endpoint in `detail` rather than adding an enum member — `reason` is a machine-readable value in the batch drop report, and this design does not need a new one.

Where it earns its keep in v1: the move planner derives its footprint from, and reports every importer refusal against, an `EdgeAnchor` per rewritten import — so a refusal says *which edge* could not be rewritten rather than which file. That is the honest minimum; it is not yet a top-level intent anchor. *Rejected alternative*: having move-symbol fan out into N edge-anchored `RewriteImportIntent`s scheduled against each other. Rejected because `MAX_PLAN_ATTEMPTS_PER_INTENT = 1` means a dependent fan-out cannot repair itself in one pass, and a partially-executed fan-out leaves dangling imports — exactly the failure mode a single all-or-nothing planner avoids.

**Landing rule**: `EdgeAnchor` ships in the *same* PR as move-symbol. The `anchors.py` docstring's deferral reason (an unconsumed export trips the self-lint gate) is a real constraint, and the gate is the arbiter.

**4. The move-symbol planner.**

`MoveSymbolIntent(symbol_id, dest_module)`; `kind = "move-symbol"`; CLI `pypeeker move-symbol <symbol-id> <dest-module>` routed through the existing `_submit_and_finish` tail, plus a `"move-symbol"` entry kind in `app/batch_intents.py`.

*Footprint*: reads the symbol and every importer symbol; writes `{symbol_id}` and the predicted destination id `{dest_module}:{leaf}`; reads+writes the source file, the destination file, and every importer/reference file (the same superset `RenameIntent.footprint` builds).

*Predicted effect*: `renamed={symbol_id: dest_id}`, `files_written={source, dest, *importers}`, and `files_created={dest_path}` when the destination does not exist. **The key modelling decision: a move is a rename in id space.** That single `renamed` entry makes `Effect.then`, `remap_id`, and every existing intent's `remap` work on moves with zero new symbol-remap machinery — which is precisely why only the *file* half of `Effect` needs new fields.

*Preconditions* (ordered, all with `slug = None` — this is a CLI op, not a `check --fix` remedy, so the frozen slug vocabulary is untouched): `SymbolResolvesUniquely` (reused) → `TopLevelDefinition` (v1 moves module-level FUNCTION/CLASS only, mirroring `DeleteSymbolPlanner._DEFINITION_KINDS`) → `MoveIsNotSelf` → `UndecoratedDefinition`/`DeletableScope`/`ScopeSpanClean` (all reused — the source-side deletion span is *exactly* delete-symbol's, so reuse the classes rather than re-derive) → `DestinationModuleResolvable` (dest maps to a path via `load_src_roots` + `module_path_from`; either indexed, or absent → created; a dest that exists on disk but is unindexed refuses as stale) → `NoDestinationNameCollision` → `AffectedFilesFresh` (reused) → `MovedBodyClosed`.

`MovedBodyClosed` is the honest v1 scoping and the one real judgment call: the moved body's free names must be satisfiable at the destination. v1 **copies** the source module's import bindings that the body actually references (derivable from the existing `FileIndex` references whose binding is an IMPORT symbol — no new analysis), and **refuses** when any free name binds to a non-import source-module symbol. Refusing beats synthesizing back-imports into the source module, which is a semantic cascade the project's "precise, not clever" principle rules out; the back-import mode is a named follow-up, not v1.

*Import rewrites — rename machinery or new edge machinery?* **Reuse the collection, not the edit builder.** A rename rewrites a token in place; a move rewrites the *module* part of an import statement, a different edit shape. So the planner reuses `find_importers`/`references_to_binding`/`import_crosses_barrel`/`imported_name_location`, and reuses `imports_ops._import_name_segments` + `ImportLineSurgerySafe` for the multi-name line case (split the moved entry out of the old line, emit a new import line). It does **not** reuse `_build_edits`, whose silent drop-on-text-mismatch (`planner.py:492-494`) would turn a missed import into a dangling one; every collected edge must produce an edit or refuse by name. The `import a` + `a.X` qualified form is **refused** in v1 (`MoveQualifiedUseUnsupported`) rather than half-rewritten.

*Barrel re-exports are rewritten unconditionally* — a deliberate divergence from rename's `--include-exports`. Architecture.md's "Re-exports are a public API surface" reasoning is about the exported *name*; a move does not change the name, only the definition's home, so rewriting `from .old import X` to `from .new import X` is repair, not cascade. Leaving it un-rewritten would break the package's public surface.

**PR split** — three PRs, each independently green and shippable:

### Acceptance criteria

- `uv run pytest -q`, `uv run ruff check src tests`, and `uv run pypeeker index src && uv run pypeeker check` are all clean at the end of every PR, with no baseline added and no change to the gated rule list in pyproject.toml.
- Each of the three PRs is independently green and shippable: PR1 and PR2 change no user-visible behavior and add no CLI surface; PR3 adds the `move-symbol` command.
- A transaction can express file creation and file deletion; `apply` and `rollback` are exact inverses over creates, deletes, edits, and a rename in one transaction, verified byte-for-byte including file absence/presence.
- Pre-flight refuses a creation whose target already exists and a deletion whose file changed since plan, leaving the transaction PENDING and the tree untouched; a mid-apply failure leaves the tree byte-identical, the transaction FAILED, and no orphan created file or `.tmp`.
- A deleted file's index entry is removed and a created file's index entry is written on apply; the inverse on rollback. No ghost index entry survives either direction.
- A transaction file written before this change (no `version` key) loads and applies byte-identically; a transaction with an unrecognised `op` or header version refuses with a machine-readable error, never a raw TypeError.
- `Effect` carries `files_created`/`files_deleted` and `then()` composes them correctly for create->delete, delete->create, create->write, and create->rename, each with a dedicated test.
- `flatten_batch` emits `FileCreateEntry`/`FileDeleteEntry` for files an executed intent's effect authorized; an unauthorized mirror-only or mirror-missing file still raises `FlattenError`, and an executed file rename still raises `FlattenError`.
- An edit against a file missing from the mirror produces a machine-readable batch drop, not an uncaught `FileNotFoundError` escaping `run_batch` (the current behavior at batch.py:611).
- The batch schedule remains input-order independent, including when a file is born mid-batch and when a destination file's on-disk existence differs; two intents creating the same path deterministically drop the later-submitted one with `CONFLICT_DROPPED`.
- `EdgeAnchor` exists in `intents/anchors.py`, is part of the `Anchor` union, is exported from the intents barrel, and is consumed by the move planner — the deferral paragraph in the module docstring is deleted, not merely edited.
- `pypeeker move-symbol <symbol-id> <dest-module>` moves a top-level FUNCTION/CLASS: the source definition is deleted, the destination module is created or extended, every `from ... import` importer (including barrel re-exports and aliased imports) is rewritten, and the whole thing is one transaction that rolls back cleanly.
- Every move refusal goes through a named `Precondition` with `slug = None` and surfaces as the CLI's standard `plan-refused` envelope; the qualified `import a` + `a.X` form and an unclosed moved body refuse by name rather than producing broken code.
- Frozen contracts verified unchanged: `TransactionSummary` field set, `check --fix` report keys, refusal-code slugs, `check` importing no `refactor`, `intents` importing only models/query/storage, barrel-only discipline, and the CLI JSON envelope (new keys are additive only).
- Exactly two pre-existing tests are modified (`tests/test_batch.py::test_created_file_is_an_error` and `::test_deleted_file_is_an_error`); every other pre-existing test passes unmodified.
- architecture.md and storage-transaction-architecture.md are updated in PR3: the `flatten_batch` walls-list entry is removed, `move` is no longer listed as roadmap, the `EdgeAnchor` deferral in structural item 1 is resolved, and the new entry formats plus header version are documented in the storage doc.

### Risks

- The applier's failure path now *removes* files (unlinking created files on restore). Its safety rests entirely on the pre-flight absence check; if that check is weakened or bypassed, the applier becomes destructive against pre-existing files. Lens A's first two attacks target exactly this, and the pre-flight check must never be relaxed for convenience.
- `_order_key` (batch.py:291) derives the schedule tie-break from `sorted(writes_files | reads_files)[0]`. A move whose destination file does not yet exist can produce a different key than one whose destination exists, so the schedule could become filesystem-dependent — directly contradicting the module docstring's input-order-independence claim. This needs an explicit test, not an assumption.
- `Effect._preimage_file` (footprint.py:328) is exact-match over `files_renamed` and knows nothing about creations. Composition bugs here are silent: they produce a wrong substitution rather than an error, and only show up as a mis-remapped anchor several intents later.
- `MovedBodyClosed` is the correctness cliff. Accepting a body whose free names resolve only in the source module produces code that imports cleanly at the destination and fails at runtime. The v1 answer is to refuse aggressively; the risk is refusing so much that move-symbol is useless in practice, which is a scoping call to make with real fixtures, not in the abstract.
- Rename's `_build_edits` silently drops locations whose text does not match (planner.py:492-494). That is correct for rename and produces dangling imports for a move. The move planner must not reuse it, and reviewers must confirm the reuse boundary held rather than assuming it did.
- Adding `EdgeAnchor`, `MoveSymbolIntent`, `MoveSymbolPlanner`, and several new preconditions adds public symbols to a codebase gated on `unused-public-symbol`, `over-exposed-module-symbol`, and `barrel-only` with no baseline. The self-lint gate is the arbiter; landing EdgeAnchor without its consumer in the same PR is the specific mistake the anchors.py docstring already warns about.
- `LoadedTransaction` changing from a tuple to a dataclass touches seven call sites across `applier`, `cli`, `registry`, and `visibility_ops`. Mechanical, but a missed site fails at runtime rather than at type-check time, since the project runs no type checker in CI.
- Scope: PR3 is genuinely large (new intent, new planner, new anchor shape, CLI command, batch-intents kind, two doc updates). If it stalls, the cut is destination-exists vs destination-created — but that cut leaves PR1 and PR2's machinery unexercised by any real feature, so it trades risk reduction for schedule only.
