# 06 — Open Decisions

The automated cleanup runs in this review series handle the mechanical work: collapsing the duplicated `SEMANTIC_TOOL_DIR` constant, hardening the test harness (an autouse cwd guard + a symbol-id builder), and fixing the two real CLI bugs (`scope`'s exit-0 error path, `privatize`'s error-grafted-onto-success payload). This memo collects what those runs deliberately left alone — items that turn on product judgment or amount to a contract change, and so need a human to decide before any code moves. Section 5 was added during integration: what looked like "safe dead code" (`_Capability`, `_LanguageAdapter`) turned out to be documented roadmap scaffolding, so its deletion became a decision too. Each entry states the decision, a recommendation, the scope and risk, and what a follow-up refactor run would do once the call is made. Details and `file:line` evidence live in `review/01`, `review/02`, `review/03`, and `review/04`; this is the sign-off sheet, not a re-derivation.

---

## 1. `convention_renames.py` — delete the unwired feature, or wire it up?

**Decision.** `src/pypeeker/refactor/convention_renames.py` is a ~280-line module (`SkipReason`, `SkippedRename`, `convention_rename_intents`, `write_intents_file`) that no `src` module imports. Its only importer is `tests/test_convention_renames.py`; `check/builtin/naming_conventions.py` mentions `convention_rename_intents` only in `:func:` docstring cross-references, never as a call. Its own docstring describes a pipeline — `check (rule) -> convention_rename_intents -> write_intents_file -> run_batch` — that was never connected. The live CLI batch path (`cli.py:604-648`) uses `app/batch_intents.build_batch_intents`, not this converter. So it is a fully-built, fully-tested feature with no production entry point.

**Recommendation: delete it.** Remove the module and its test together, and scrub the two `:func:` xrefs in `naming_conventions.py:9,159`. If convention-driven mass rename is genuinely on the roadmap, the counter-move is to wire it in — connect `convention_rename_intents`/`write_intents_file` into a CLI command or into the `naming_conventions` fix path — which promotes the four symbols to real public API. Pick one. Do **not** just privatize the names; that buries the design question instead of answering it.

**Scope / risk.** Deleting is low-risk and self-contained: one source module, one test file, two docstring edits. Nothing else imports it, so `check` and the barrels stay green. Wiring it in is a real feature commitment with its own design and test surface. The only cost of getting this wrong is deleting something the team quietly wanted — hence the sign-off.

**What a refactor run would do.** On "delete": remove `refactor/convention_renames.py` and `tests/test_convention_renames.py`, drop the two xrefs in `naming_conventions.py`, then re-run `uv run pytest -q` and the self-lint. On "wire in": that becomes its own feature task, out of cleanup scope.

## 2. `.semantic-tool/` -> `.pypeeker/` on-disk rename (and the `semantic-tool` binary alias)

**Decision.** Two independent identity leftovers from the working title, which should be decided separately.

**2a — the on-disk directory.** The design note in `storage-transaction-architecture.md:15-24` frames this as a migration that "invalidates existing indexes." That framing is broader than the facts: the entire `.semantic-tool/` tree is gitignored (`.gitignore:31`), so nothing under it is committed and the blast radius is a single developer's local working copy, not the fleet. Indexes and `tree.json` regenerate in seconds via `pypeeker index src`. The only stateful, non-regenerable artifacts are pending **transactions** (rollback anchors) and the **check baseline** (the ratchet) — and both are also per-developer local state, never shared through git.

Three options: **(1) leave as-is** and just tighten the docs; **(2) rename-with-read-fallback** — write `.pypeeker/`, fall back to reading `.semantic-tool/` when the new dir is absent, accept both names as project-root markers, and lazily migrate on the next `index`; **(3) hard rename** — write and read `.pypeeker/` only, paired with a version bump and a release note telling users to `mv .semantic-tool .pypeeker` to keep pending transactions and their baseline.

**Recommendation: Option 2 (rename with read-fallback), gated behind first doing the DRY collapse** described in `review/04 §4` and `review/01 §1`. The directory name is currently spelled four independent times in `src` (`index_store.py:15`, a duplicate in `transaction_store.py:24`, and hardcoded literals in `indexer.py:19` and `check/baseline.py:67`); collapse those to one name-neutral `STORAGE_DIR` constant first — it's an independently valuable, behavior-preserving refactor — so the rename becomes a one-line value change plus the fallback branch rather than a four-site hunt. Option 2 is the only choice that preserves in-flight rollback anchors and the ratchet without asking every developer to run a manual `mv`. Option 1 is the honest fallback if the team decides the churn isn't worth it (still do the DRY collapse, just improve the docs). Option 3's sharp edge is a silently-reset baseline — the ratchet quietly forgets its history — which is exactly why the fallback is worth the extra branch.

**2b — the `semantic-tool` binary alias** (`pyproject.toml:14`, a second console script pointing at the same `main`). Nothing in this repo depends on it: CI, the Dockerfile, CLAUDE.md, and every test invoke `pypeeker`. The only possible consumer is external muscle memory. **Recommendation: drop it** (single-name product, zero internal dependents), or keep it one release behind a deprecation note — either way a one-line change with no coupling to 2a.

**Scope / risk.** 2b is a docs-tier, one-line change, zero risk. 2a Option 2 touches the four constant sites plus ~35 test path hardcodes (`review/04 §1c`) and adds a small fallback resolver injected through the `cli.py` composition root like the existing stores; moderate risk concentrated in the fallback precedence logic (which dir wins when both exist, whether to clean up the old one). The DRY-collapse prerequisite is very safe.

**What a refactor run would do.** First, the standalone DRY collapse: one `STORAGE_DIR` constant, delete the duplicate, replace the two literals. Then, for Option 2: `STORAGE_DIR = ".pypeeker"` + `LEGACY_STORAGE_DIR = ".semantic-tool"`, a resolver that writes new and reads whichever exists, both names in `PROJECT_MARKERS`, migrate the test hardcodes through a shared fixture/constant, rename the `test_finds_semantic_tool_dir` test, and update the docs listed in `review/04 §5`. Add coverage for the fallback and for a pre-existing `.semantic-tool/` still resolving with an un-reset baseline. Separately, delete the `pyproject.toml:14` alias line.

## 3. CLI error-envelope standardization + declaring the symbol-ID grammar and CLI JSON envelope FROZEN

**Decision.** The two concrete CLI bugs — `scope` returning an error with exit 0, and `privatize --apply` grafting an `error` key onto an otherwise-success payload — are already being fixed by the automated run. This decision is about the *broader redesign* those bugs point at, which is a contract change and needs sign-off: (a) unify the machine-code key (today `demote`/`promote` use `"code"`, `purity` uses `"reason"`, `plan-batch` drop records use `"reason"` for a third meaning) into a single, always-present error shape; (b) optionally adopt a uniform top-level `{ok, data}` / `{ok, error}` envelope so consumers stop having to type-sniff array-vs-object responses; and (c) write down the symbol-ID grammar and the CLI JSON envelope as **frozen contracts** with additive-only evolution.

**Recommendation: standardize the error branch first (Option B), leave success payloads byte-stable, and declare both contracts frozen in writing.** Every listed inconsistency — the eight distinct error envelopes, the `code`-vs-`reason` key drift, the two bugs — lives on the error branch, so fixing just errors removes all of it while keeping churn mechanical (~35 error assertions across ~10 test files; the three exact-dict *success* equalities stay untouched). Standardize on `{"error": {"code", "message", ...extra}}` with a closed set of `code` values behind one shared `_emit_error` helper. Defer the full `{ok, data}` wrapper (Option A) to a separate, deliberate breaking bump behind a flag or major-version boundary — it adds ~120 success-side assertion changes and byte-breaks downstream scripts for a uniformity win that isn't urgent. On the freeze: the symbol-ID grammar is *already* frozen in practice — ~1039 hand-typed literals across 54 test files make any change a suite-wide event — so the real choice is "frozen by accident vs frozen by intent." Declaring it (and the envelope, and the persisted baseline-file schema) frozen in the docs CLAUDE.md already points to is cheap and makes every future change intentional. Pair it with the test-side helpers from `review/03 §5c` (a symbol-ID builder, an envelope-shape assertion helper) so the contract is enforced in one reviewed place instead of a thousand literals.

**Scope / risk.** Error standardization: ~18 source error sites collapse to `_emit_error`, ~35 test assertions rewritten (mostly `output["error"]` -> `output["error"]["message"]`, plus promote/demote's `output["code"]` -> `output["error"]["refusal"]` and purity's `reason` moving under `error`); roughly half a day, low risk, mechanical. Freezing the contracts is a documentation change with no code risk. The full `{ok, data}` envelope is the higher-blast-radius item and is explicitly *not* recommended for this cleanup pass.

**What a refactor run would do.** Add `_emit_error(code, message, *, exit_code=1, **extra)` to `cli.py`, define the closed code set, convert the ~18 error sites, and update the ~35 error assertions plus a table-driven regression test asserting every command's error output carries `error.code` + `error.message` + a non-zero exit. Add the frozen-contract statements to the design docs and the symbol-ID/envelope test helpers, migrating the highest-concentration test files first. The `{ok, data}` wrapper and an opt-in `check --json` mode are noted as separate, later, deliberately-gated changes.

## 4. The 22-symbol privatize batch (test-only public symbols) — privatize which, keep which?

**Decision.** `pypeeker privatize --include-heuristic` nominates 22 symbols; the no-flag run skips all of them as `heuristic-confidence` and applies nothing. The tool cannot tell, on its own, which nominations are genuine over-exposure and which are intentional public surface. This needs a human to sort them into keep vs privatize. `review/01 §4` classifies all 22:

- **Category C — leave public (7 rule functions):** `require_docstrings`, `no_unresolved_refs`, `prefer_tuple`, `import_boundaries`, `unused_public_symbol`, `no_impure_functions`, `pure_decorator_contracts`. Each is reached through a registry dict or a `@register_rule` decorator and dispatched by name at runtime — invisible to the static rule, hence the heuristic skip. Privatizing them churns ~30 test imports for zero benefit and risks masking the dispatch. **Never touch.**
- **Category D — keep public (3 result types):** `BatchResult`, `ExecutedIntent`, `DropReason` are the return surface of the barrel-exported `run_batch`; callers hold instances even without importing the names. **Keep.**
- **Category B — the actual candidates.** Split two ways: **over-exposed-only** (`Schedule`, `schedule`, `ConflictReport`) live entirely within their own module and no test imports them; and **test-only exports** (`materialize_mirror`, `ScheduleCycleError`, `ConflictKind`, `OrphanReason`, `PlannableFix`) whose public name is imported only by `tests/`.

**Recommendation: privatize the three over-exposed-only symbols; keep everything else public.** Rename `Schedule`/`schedule`/`ConflictReport` to `_`-prefixed names and drop them from their module `__all__` — no test touches them, so it's source-only and clean. The one caveat is that `batch.py`'s module docstring advertises `schedule` as a "pure public" primitive, so confirm that seam is not intentionally exposed before privatizing it. For the five test-only exports, **leave them public as intentional test seams**: privatizing each forces the cited test import to switch to a `from ... import _x as x` alias, and the churn-to-benefit ratio is poor unless shrinking `__all__` is itself a goal. Categories C and D are not candidates at all.

**Scope / risk.** The three over-exposed-only renames are low-risk, source-only, validated by pypeeker's own `barrel-only` and `unused-public-symbol` self-lint. The five test-only privatizations (if the team wants them) are coordinated source + test edits following the mechanical alias pattern task-97 already used. Touching Category C would churn ~30 test imports and risk hiding the dynamic dispatch — the reason it's a hard "never."

**What a refactor run would do.** Rename `Schedule`, `schedule` (`batch.py`), and `ConflictReport` (`footprint.py`) to `_`-names, remove them from their `__all__`, re-run the self-lint and `pytest -q`. Leave the 7 rule functions, the 3 `run_batch` result types, and the 5 test-only exports untouched. If the team later decides to shrink `__all__`, the five test-only exports become a follow-up with the alias-import test edits spelled out in `review/01 §4`.

## 5. `_Capability` / `_LanguageAdapter` — delete the dead scaffolding, or keep it as reserved roadmap?

**Decision.** `review/01` flagged both as "safe, high-value" dead code: `_Capability` (`models/capabilities.py`, 9 members, zero consumers, its only referent a single assertion in `tests/test_models.py`) and `_LanguageAdapter` (`adapters/base.py`, a `Protocol` with zero code referents). The adversarial verify on the cleanup run caught what the analysis pass missed: **both are documented, deliberate multi-language roadmap scaffolding**, not accidental cruft. `architecture.md` describes the `Capability` model as "reserved for the multi-language roadmap" and presents `LanguageAdapter` as the adapter contract; there is also an apparent prior decision (task-69) to keep the enum reserved rather than delete it. So this is a design judgment — "do we keep the not-yet-wired multi-language seam?" — not janitorial work, which is why the automated run held it.

**Recommendation: delete both, and treat the multi-language capability model as a design idea that lives in `architecture.md`, not as unused code.** Zero-consumer scaffolding that predates any second language is speculative generality; git history preserves it, and re-introducing a one-enum + one-Protocol seam when a real second adapter arrives is cheap and better-informed. Keeping dead code "for the roadmap" is precisely the pattern this tool's own `unused-public-symbol` rule exists to surface. **But this reverses a recorded decision, so it needs your sign-off** — if the team considers the seam load-bearing for near-term multi-language work, the counter-move is to keep both, rename the doc references to the current `_Capability`/`_LanguageAdapter` spelling, and retain the "reserved roadmap" framing (this was `review/05`'s original plan).

**Scope / risk.** The deletion itself is low-risk and was already implemented and in-scope-verified by the cleanup run (delete the enum + its one test assertion; delete the `Protocol` + its now-unused imports; keep `adapters/base.py` as a docstring-only boundary note because `python_adapter.py:8` cross-references the module). The real coupling is **documentation**: the `docs` slice (`review/05`) must move in lockstep — on "delete", the doc must stop enumerating the enum's members and stop describing the protocol (the cleanup run's docs draft did this but left the member list at `architecture.md:~139` intact, an internal contradiction to fix); on "keep", the doc keeps the reserved framing at the `_`-spelling. The two must land together or the docs describe a state the code isn't in.

**What a refactor run would do.** On "delete": land the held `dead-code` enum/protocol edits (`models/capabilities.py`, `tests/test_models.py`, `adapters/base.py`, `adapters/__init__.py`) plus a one-line fix to the `python_adapter.py:8` cross-reference, together with the reconciled `docs` slice (member list removed, capability model relabeled as roadmap prose). On "keep": discard those edits and apply `review/05`'s underscore-rename docs framing instead. Either way, run `pytest -q`, `ruff`, and the self-lint.
