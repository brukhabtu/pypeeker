## Design

ONE HOME: `src/pypeeker/project.py`.
Rationale: it is the only module every consumer can legally reach — `dsl` allows `project` (pyproject.toml:146), `cli` is unconstrained, and `project` itself allows nothing, so a coercion there cannot create a cycle. It also folds in the sixth copy (`_as_str_tuple`), which AC #3 requires and which a `dsl`-side home structurally cannot. Rejected: `dsl/config.py` (leaves `project._as_str_tuple` as a second implementation, and `refactor`'s `load_visibility_config` path keeps its own divergent tolerance); a new top-level `config` package (strict mode demands a new allow-table row plus `refactor`/`app` allowances for one exception class — cost with no benefit over `project`).

ERROR TYPE: `ConfigOptionError(ValueError)` defined in `project.py`, carrying `option`, `value`, `expected`, and `code = "config-option"`.
Rationale: it must live where `project` can raise it, and `project` cannot import `dsl.errors`. It is NOT a `DslError` subclass — `DslError` exists for *expression-authoring* mistakes and is rendered through `cli._emit_error`'s JSON envelope on `query`/`purity` (cli.py:712-715); a `[tool.pypeeker]` misconfiguration is a *usage* error, and `check` already renders its two config refusals (`BoundaryConfigError`, `UnknownExpressionError`) as `click.UsageError` (cli.py:473-484). Following that established shape leaves the frozen CLI-envelope/refusal-code contract untouched.
Rejected: enriching the message with the offending rule id by intercepting in `check_run._run_rules` / `privatize`. AC #2 asks for the option and the accepted values, not the rule; the enrichment costs `app` an import it cannot make from `project` (needs a `dsl` barrel re-export) plus two interception points, for information a user finds by searching the key in `pyproject.toml`. Recorded as a follow-up, not done here.

THE ROOT CAUSE OF THE 3-vs-0 IS A KEY COLLISION, NOT THE COERCION. Loud coercion alone would turn the reproduced case into a hard refusal on every project that legitimately declares `[tool.pypeeker.visibility]` — which fails AC #1 ("gets the SAME require-docstrings findings as one without it"). So the injected project-wide table moves to a reserved key no rule option can collide with:
`PROJECT_VISIBILITY_KEY = "project-visibility"` in `project.py`, written by `dsl/config.read_config` and `app/privatize.run_privatize`, read by `dsl/visibility._visibility_table`. `read_config` **refuses** (rather than silently strips) a rule table that writes that key itself, so it cannot be shadowed.
Rejected alternatives: (a) type-sniffing the `visibility` option (Mapping => project table, list => enum option) — exactly the silent guessing this task kills; (b) renaming `require-docstrings`' own `visibility` option — a user-visible config break; (c) passing the project table as a second argument to every rule builder — ripples through `DslRule.build`, `RulePart`, `PortedRule.findings/remediations`, `privatize_selections` and every mutation rule, for one key.

THE ONE IMPLEMENTATION — three entry points over one core:

1. `coerce_str_list(option: str, raw: Any, *, allow_scalar: bool = True) -> tuple[str, ...]`
   - `None` -> `()`; `str` -> `(raw,)` or `()` when empty, **only when `allow_scalar`**; `list`/`tuple` -> `tuple(str(v) for v in raw)`; everything else (Mapping, int, float, bool) -> `ConfigOptionError`.
   - `allow_scalar=True` (default) preserves the frozen rule-option convenience pinned by tests/test_dsl_rules.py:247 (`kinds = "class"` is one value, not five characters). `allow_scalar=False` is used for the three top-level list keys `rules`/`plugins`/`src`, which are lists by contract and where a bare string is the reported bug. This one keyword is the *entire* axis of difference, which is why this stays one function rather than two.
   - Keeping `str(v)` per element (rather than refusing a non-string element) is deliberate: frozen behaviour, harmless, changes no finding.

2. `coerce_enum_set(option: str, raw: Any, enum_cls: type[Enum], *, default: Sequence[str] = (), choices: Collection[Enum] | None = None) -> tuple[Enum, ...]`
   - Coerce through `coerce_str_list(option, raw)` (scalar allowed). If the result is empty, coerce `default` instead — this is C's and D's "absent or empty falls back to the default".
   - Every remaining name must parse via `enum_cls(value)` and, when `choices` is given, be in `choices`; otherwise **refuse**, naming the option, the offending value, and `sorted(m.value for m in (choices or enum_cls))`.
   - Dedupe, **written order** (drop C's sort — see risks).
   - This single definition collapses C, D and E. The asymmetry D's docstring defends (non-empty-but-all-unparseable -> empty set) *cannot arise any more*, because the first unparseable entry refuses. That is the simplification, and it is why the enumeration matters: three sites documented three different silences for the same question, and refusal makes the question moot.

3. `coerce_visibility_table(raw: Any) -> Mapping[str, Any]` — the shape check both readers share.
   - `None` -> `{}`; non-`Mapping` -> `ConfigOptionError` (naming `[tool.pypeeker.visibility]` and "a table"); `mode` present and not in `VISIBILITY_MODES` -> refuse naming the accepted `("app","library")`; a key outside `{"mode","public-roots","allow-decorators"}` -> refuse naming the three accepted keys (this is what catches `public_roots` vs `public-roots`, today a silent no-op).
   - `project._parse_visibility_config` and `dsl/visibility._visibility_table` both call it, so the two readers stop disagreeing (today one silently defaults, the other raises a bare `TypeError`). `_visibility_table` keeps its extra sentence about a parsed `VisibilityConfig` — that refusal survives, upgraded from `TypeError` to `ConfigOptionError` (a `VisibilityConfig` is not a `Mapping`, so it refuses for free).

WHY `src` KEEPS ITS SENTINEL: `read_config`'s docstring (dsl/config.py:62-67) defends the distinction between an *absent* `src` (default `("src",)`) and an explicit `src = []` (no prefix filter, whole corpus). Coercing `section.get("src")` would erase it. Keep `section.get("src", DEFAULT_SRC)` and route only the retrieved value through `coerce_str_list(..., allow_scalar=False)`.

CLI SURFACE: `cli.py` imports `ConfigOptionError` from `pypeeker.project` (cli is unconstrained) and catches it in `check` (beside cli.py:473-484) and in `privatize` (~cli.py:1414, which today has no try at all), rendering `click.UsageError`. No `_emit_error`, refusal-code or JSON-envelope changes.

## Risks

- Self-lint zero-baseline gate (FROZEN). `unused-public-symbol` and `over-exposed-module-symbol` are gated (pyproject.toml:90-91) and read the injected table via `_merged_allow_decorators` (dsl/visibility.py:351-355) to honour `allow-decorators = ["main.command", ...]` (pyproject.toml:98-99). If the injection key rename lands in dsl/config.py:83 but not in dsl/visibility.py:339 (or vice versa), those allow-decorators stop reaching the rules and the gate goes red with a wall of new findings on cli.py's Click commands. This is the highest-value check after implementation.
- Scope of the visibility-table loudness reaches `refactor`, not just `check`. `project.load_visibility_config` (project.py:95-98) is called from refactor/visibility_ops.py:114, so `pypeeker demote`/`promote` on a project with a typo'd `mode` or a `public_roots` key will now refuse where it previously ran. Intended behaviour, but a user-visible change to two commands the task does not name, and cli.py's `demote`/`promote` have no `ConfigOptionError` catch (step 11 covers only `check` and `privatize`), so it surfaces as a traceback. A reviewer should decide whether to extend the catch there or accept the traceback; the plan leaves it out to bound the diff.
- AC #2's "naming the option" is satisfied with the bare option key, not the rule id. `_merged_allow_decorators`, `coerce_enum_set` etc. are shared across rules, so "option 'kinds': 'bogus'" does not say WHICH rule's `kinds`; a project setting `kinds` on two rules gets an ambiguous message. The rejected enrichment (intercepting in `check_run._run_rules`, which knows `name`) is the fix if a reviewer judges the AC unmet; it costs a `dsl` barrel re-export because `app` may not import `project` (pyproject.toml:148).
- Test churn volume is the main correctness risk, not the source change. ~25 test sites pass `{"visibility": {...}}`, and TWO of them (tests/test_check_rules.py:30, tests/test_dsl_rules.py:211) must NOT be renamed because there `visibility` is the rule's own enum option. A blind find-and-replace across tests/ breaks exactly the two tests that prove the collision is gone, and does so by making them pass for the wrong reason.
- Refusing unknown keys in `[tool.pypeeker.visibility]` (step 4) is the one change no AC demands. It is the highest-value usability fix in the set (`public_roots` for `public-roots` is silently inert today) but also the only place a previously-working real-world config starts refusing for a reason unrelated to the reported bug. If a reviewer wants a narrower diff, this is the piece to drop; L6's ledger entry then covers only the non-Mapping and `mode` cases.
- Dropping `_selected_kinds`'s `sorted(...)` (visibility.py:319) for written order changes what appears in a derivation's `rhs` for the visibility family's `kinds` clause. No finding changes (the only consumer is `Expr.is_in`, whose test is membership either way) and no cache key derives from it, but any test asserting on a rendered derivation for those rules would move. Grep for `is_in` in derivation assertions before assuming none exists.
- `coerce_enum_set` parses its own `default` through the same refusal path, so a default tuple that does not parse becomes a hard failure at rule-build time rather than a silent empty set — intended, but it means a typo in `_DOCSTRING_KINDS_DEFAULT` / `_DEFAULT_KINDS` / `_NAMING_KINDS_DEFAULT` now breaks the run instead of quietly disabling a rule. Verify all three parse under their `choices` (`_DEFAULT_KINDS` = function/class against `_KIND_CHOICES` = function/class/variable; `_NAMING_KINDS_DEFAULT` = function/method/class against `frozenset(_DEFAULT_CONVENTIONS)`'s six). Both hold today, but the plan makes it load-bearing.
