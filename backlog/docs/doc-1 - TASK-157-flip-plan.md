## Design

**The organizing constraint.** `scripts/differential-check.py:run_old_engine` drives the *CLI* for its old side. So the oracle and the CLI rewiring cannot coexist: the last meaningful oracle run must happen **before** `cli.py:check` changes, and the oracle must be deleted in the same working-tree state that rewires it. Everything else follows from that.

Hence a two-phase working tree, verified differently in each phase:

- **Phase A — additive, oracle stays authoritative.** Build every surviving module *beside* the frozen code without touching `cli.py`'s check/privatize wiring. `scripts/verify-repo.sh` (all five steps, oracle included) must stay green after each step. Any output-moving mistake here is caught by the thing built to catch it.
- **Phase B — the cutover.** Rewire, delete, port tests, update docs, in one motion. From here on the gate is `pytest + ruff + self-lint`, and the self-lint is now the new engine gating itself.

**Decisions, with rationale.**

*1. The baseline file moves to `storage/baseline.py`, not to `app/`.* Both `dsl` (which must *read* the born-private ratchet) and `app` (which must *write* it, and owns the violations namespace) need it, and `dsl` may not import `app`. `storage` is a leaf both already allow, it already owns `resolve_storage_root`, and the file is a `.pypeeker/` artifact. This discharges deferred item (2) in a stronger form than the ledger asked for: `dsl/visibility.py`'s `_storage_root` **and** `_baseline_document` copies both die, and `resolve_storage_root` reaches the barrel because the only deep importer that blocked it (`check/baseline.py:65`) is being deleted. Rejected: keeping it in `app` (forces a second file-format copy in `dsl`); a new top-level `baseline` package (a new strict-mode allow-table entry for one module).

*2. Baseline identity re-keys to `(rule_id, anchor_id)` by adding `anchor_id` to `Finding` with `compare=False`.* `_render:340` already holds `match.anchor`. `compare=False` is mandatory, not stylistic: the read half's tests assert whole-`Finding` equality and would all break otherwise, and it mirrors what `remedy` and `decision` already do for the same reason. Identity string becomes `f"{rule}::{anchor_id}"`; the `identity -> count` storage format, the surplus-attribution and `fixed_identities` logic in `delta`, and the `"violations"`/`"symbols"` namespace split all survive unchanged. `_normalize_message`'s `(line N)` regex dies with the message-based key — which is the point of fork #6, and what makes `test-only-production-code`'s already-ledgered message change safe. This discharges the standing `*(planned, lands at flip)*` ledger entry.

*3. `dsl/config.py` is rebuilt on `pypeeker.project`, and `dsl` gains `project` in its allow-list.* The hand copy's sanction is explicitly conditional — the module docstring and `dsl/differential.py:23-31` both say it exists so the new side never executes old-engine code while the oracle grades it. Once the oracle is deleted that sanction expires, and keeping the copy would leave two config readers with nothing to keep them honest. `read_config` grows to return `(src, rules, plugins, options)` and is exported from the `dsl` barrel so `app` can reach it through one owner. Rejected: giving `app` `project` and a second loader — that recreates the drift the flip is deleting.

*4. `app` swaps `check` for `dsl` in its allow-list; the `dsl-fix-engine.py` composition moves into `app/`.* `app` is defined as the layer allowed to import both a rule engine and `refactor`; that was `check` and becomes `dsl`. The composition currently exiled to `scripts/dsl-fix-engine.py` (its docstring says it lives there only so phase 4 adds no `app`→`dsl` edge) comes home as `app/fix_run.py`. `dsl` still imports neither `app` nor `refactor`.

*5. Custom rules survive: `dsl` gets a registration overlay.* `[tool.pypeeker].plugins` + `@register_rule` is a shipped, tested (`test_check_engine.py:96-180,308`), documented public extension point. Dropping it silently would be a real capability regression hidden inside a refactor. `RULES` stays the closed builtin table; add a module-level `_REGISTERED: dict[str, PortedRule]` plus `register_dsl_rule(rule)` and make `dsl_rule` check the overlay first — the exact precedence `analysis/traits.py:register_trait` and `refactor/registry.py:register_planner` already use, which CLAUDE.md names as the convention. Plugin *import* stays in `app` (it needs `sys.path` manipulation against the project root, which is composition, not DSL). Rejected: dropping the feature with a ledger entry (loses a public contract for no design gain); a bare `RULES` mutation (no precedence rule, no shadow refusal).

*6. An unknown configured rule name refuses loudly.* `CheckEngine.run:59-66` silently skips it today — a typo'd rule id reads as a clean run. `dsl_rule` already raises `UnknownExpressionError` naming the known ids. Resolve rule names *after* plugin import and let the refusal surface as a `click.UsageError`, the same shape `BoundaryConfigError` already gets at `cli.py:463-467`. This is a deliberate, user-visible improvement and needs a ledger entry; it is safe here because all 11 gated rules are among the 22 claimed (verified).

*7. `check --fix`'s DECLARED gate is not re-implemented — it is already structural.* All five repair mutations carry `floor=Confidence.DECLARED` (`terminals.py:469-553`), so `auto_fixable`'s two conjuncts are exactly "the mutation produced an intent". `app/fix_run.py` iterates `rule.remediations(...)` and never writes a confidence test. This is the already-ledgered phase-4 divergence (floor decides whether a remedy *exists*), now load-bearing.

*8. The fixpoint's rule narrowing replaces `SIMULATION_UNSAFE_RULES` with "rules that declare a mutation".* The constant exists only because `born-private` self-seeds through the real project root under an overlay; the ported rule does not write at all. Output-neutral by construction — `_plan_pass` only ever consumes remedies, and a rule with `mutation is None` yields no `Remediation` — and it is strictly cheaper. The constant, its module and its barrel export all go.

*9. born-private's self-seed moves to the app layer as a DSL selection.* The ledgered phase-3b divergence ("the divergence is the write, and only the write") closes here. Add `born_private_surface()` to `dsl/visibility.py` — the shared `_candidate_clauses` prefix minus the `BASELINE_NAMESPACES` gate and minus the `RECORDED_PUBLIC_SYMBOLS` negation, projecting `symbol_id` — and have `app` seed from it when `born-private` is enabled and the `"symbols"` namespace is absent, plus on `--update-baseline` after `clear_symbol_baseline`. Expressing the seed as the *same* selection the rule's candidate clauses use is what stops the surface and the ratchet drifting.

*10. `privatize` becomes `privatize_selections` → intents → the batch machinery; `refactor/privatize.py` keeps its pre-filter minus what moved.* `DEMOTE`'s two pointwise preconditions (`dunder-or-main`, `already-private`, in the frozen order) and the confidence floor now live on the mutation, so `_demote_candidates`' first three tests (`heuristic-confidence`, `dunder-or-main`, `already-private`) are deleted from `refactor/privatize.py`; the other five (`not-found`, `ambiguous`, `hierarchy-unsafe`, `protected-public-api`, `name-collision`, `pending-collision`) stay, because they need the query engine, the class hierarchy, library-mode config, or batch-level state and are not pointwise. `_demote_intents`' hand-built `RenameIntent` is deleted; `ChangeVisibilityIntent(direction="demote")` from `DEMOTE` is the only demote intent in the system, and `VisibilityPlanner` re-validates. Skip reasons that now come from a `MutationDecision` are mapped back onto the existing `_SkippedSymbol` codes so the `privatize` JSON keeps its shape.

*11. `privatize --include-heuristic` is removed, with a ledger entry.* Fork #2 puts the floor on the shared mutation value; a per-invocation floor override would mint a second `DEMOTE` and is exactly the drift the fork exists to prevent. This is the one CLI *option* removal in the flip and must be called out explicitly rather than discovered by a user.

*12. Findings are sorted `(path, line, rule, message)` before the CLI prints them.* `Violation` is `order=True` and `CheckEngine.run:92` sorts; `Finding` is not ordered and the DSL returns rows in per-rule index order. Without an explicit sort, `check`'s printed line order changes for no reason. Do it once, in the app-layer run service.

*13. The two deferred `dsl` renames.* `dsl/mutation.py` → `dsl/mutation_rules.py` (it is the rule family; `Mutation` the repair value stays in `terminals.py`). `dsl/differential.py` → `dsl/engine.py` and `dsl/differential_fix.py` → `dsl/repairs.py` — these are the new engine's runnable surfaces, and "differential" names an oracle that no longer exists. Both are pure renames plus barrel/docstring updates; do them **last**, after the deletions, so no rename churn lands in the middle of the cutover diff.

*14. Test port policy: a DSL twin of `run_rule_on_store`, then scenario-by-scenario.* Add `run_dsl_rule_on_store(rule_id, store, options) -> list[Finding]` and a `run_dsl_rule` fixture to `tests/conftest.py`. With `Finding.__str__` byte-identical to `Violation.__str__` and the same five fields, most of the 259 `test_rule_*` scenarios reduce to: swap the private rule-function import for a rule id, swap `Violation` for `Finding`, and rename `.file_path` → `.path`. Tests of *private frozen helpers* (`_to_snake_case`, `_rename_pair`, `_import_submodules`, `_born_private` — inventoried in `review/03-test-coupling.md`) have no port target and each needs either a home on the DSL side or a ledger line. Every deleted test file must leave a ledger entry stating where its scenarios went; AC #2 is graded on that, not on the file count.

**What is deliberately NOT changed:** the `check --fix` report keys and their types, refusal codes, `TransactionSummary`, the `.pypeeker/check-baseline.json` on-disk *format* (namespaces, `identity -> count`, sorted+indented), the `privatize` JSON keys and skip-reason codes, `barrel-only` discipline, and the zero-baseline self-lint gate.

## Risks

- **The oracle dies the moment the CLI is rewired.** `scripts/differential-check.py:run_old_engine:1395` and `run_old_fix_engine:1421` shell out to `pypeeker check` / `pypeeker check --fix --plan`. If B1 lands before the harness is deleted, the harness compares the new engine against itself and reports a vacuous PASS — the most dangerous possible failure mode, because it looks like success. Phase A/B separation exists entirely for this; a reviewer should check that no working-tree state has a rewired `cli.py:check` alongside a live `differential-check.py`.
- **`app/privatize.py:82` injects a parsed `VisibilityConfig`; `dsl/visibility.py:_visibility_table:320` raises `TypeError` on exactly that.** Copying the frozen injection into the new privatize service crashes at runtime on any project declaring `[tool.pypeeker.visibility]` — which includes this repo. It must inject the raw mapping. This is the single most likely straight-copy bug in step A12.
- **`SIMULATION_UNSAFE_RULES` removal rests on an argument, not a measurement.** The claim is that `_plan_pass` only ever consumes remedies, so narrowing loop iterations to mutation-declaring rules is output-neutral. It holds today because `born-private` declares no mutation — verify that against `dsl/rules.py:RULES` rather than assuming, and note it stops holding the day someone gives `born-private` a repair.
- **The fixpoint port is a 175-line transcription with four interacting guards** (`quiescent` / `repeated-fix` / `cycle` via `_simulated_state_hash` / `max-iterations`) and a non-obvious `fixes` vs `reverted` partition whose invariant is 'fixes non-empty iff tx_id set'. `tests/test_check_fix_until_clean.py` (42 scenarios) is the only thing that pins it; port those tests *before* trusting the transcription, not after.
- **Baseline re-key silently invalidates existing baselines.** Already declared in the ledger ('none known in the wild'), but the failure is quiet: an old baseline file's `"violations"` keys simply never match, so every finding reads as new. Consider emitting a one-line note when `load_baseline` returns a non-empty map whose keys contain `'::'` three times (the old shape) — cheap, and turns a confusing regression into a message.
- **`(rule_id, anchor_id)` can collide where the message-based key did not.** Multi-part rules fan one row into several findings; `docstring-drift`'s ghosts anchor on `<function id>:<param>` (verified via the ledger) so they are distinct, but `naming-conventions`' two message shapes and `import-boundaries`' parts should be checked. The `identity -> count` storage tolerates collisions the same way it always did, but a collision silently weakens the ratchet's granularity.
- **Refusing an unknown configured rule name is a behaviour change that can break a user's config on upgrade** — today `CheckEngine.run:59-66` ignores it. Safe here (all 11 gated rules are claimed, verified) but it is a new failure mode for consumers, and the refusal must name the known ids or it is worse than the silence it replaces.
- **Deleting `privatize --include-heuristic` removes a shipped CLI option.** Not covered by the frozen list (which names JSON envelopes and refusal codes), but it is the one user-facing capability the flip drops. If that is unacceptable, the alternative is a second `DEMOTE_INCLUDING_HEURISTIC` value — which is precisely the fork-#2 drift the design forbids, so the decision should be made deliberately rather than discovered in review.
- **`refactor/privatize.py` is not frozen but is load-bearing, and step A13 removes three of its eight skip branches.** `tests/test_privatize.py`, `tests/test_promote_demote.py` and `tests/test_privatize_cli.py` (17) all assert on skip reasons; a reason that moves from the pre-filter to a `MutationDecision` must still surface under the same code in the CLI JSON, and the ordering (`dunder-or-main` before `already-private`) is deliberate — `_demote_candidates:308` documents why.
- **Scale.** ~7500 production LOC deleted, ~7000 test LOC in motion, 3896 tests, 12 rule-test files to port scenario-by-scenario, plus three docs. The program mandates one PR, so it cannot be split across PRs — but the implement stage should be split into sequential segments (A2-A8 substrate, A9-A13 services, B1-B7 cutover, B8 tests, B9-B12 docs) with a gate run between each, or the failure signal becomes uninterpretable.
- **AC #2 is the weakest-graded criterion.** 'One-for-one home or a ledger entry' has no mechanical check once the oracle is gone. The `review/03-test-coupling.md` private-helper inventory is the best available checklist for the tests with no natural DSL home; anything ported by deletion without a ledger line will pass CI and fail the acceptance criterion.
