# Audit CLAUDE.md

CLAUDE.md is only useful if its claims are true. This skill checks every factual
claim in CLAUDE.md against the repo it describes and fixes what has drifted —
without rewriting the file wholesale.

## What counts as a factual claim

Walk CLAUDE.md section by section and pull out anything that is checkable, not
just descriptive prose. That includes:

- **Commands** — every fenced `bash` snippet (`uv run pytest -q`, `uv run ruff
  check src tests`, `uv run pypeeker index src && uv run pypeeker check`, the
  `scripts/verify-repo.sh` entry point, etc.)
- **File and directory paths** — `architecture.md`, `storage-transaction-
  architecture.md`, `.pypeeker/`, `.claude/workflows/task-pipeline.js`,
  `.claude/workflows/versions/`, `.claude/workflows/PIPELINE-GUIDANCE.md`,
  `scripts/verify-repo.sh`, module paths like `adapters/python_adapter.py`,
  `binder/`, `refactor/cst.py`, `analysis/traits.py`, `check/models.py`, etc.
- **Rule counts and self-lint claims** — "11 rules today", "zero findings",
  which rules are excluded and why.
- **The module-layering table** — the bottom-up package list and each
  package's allowed imports under "Enforced module layering".
- **The test-suite size** — "~90 files under tests/".
- **The CI description** — what `.github/workflows/ci.yml` actually runs and
  on what triggers.
- Anything else phrased as a fact about the repo's current state rather than
  as a design rationale or convention statement.

## How to verify each claim

- **Commands and rule sets → `pyproject.toml` is the source of truth.**
  Check `[tool.pypeeker]` (rule list) and `[tool.pypeeker.import-boundaries]`
  (the `allow` table and `unconstrained` list) against what CLAUDE.md says.
  Use Grep/Read on `pyproject.toml` directly — do not infer from memory or
  from architecture.md.
- **Paths → the actual tree.** Use Glob/Bash (`ls`, `find`) to confirm a
  referenced file or directory still exists at the claimed path.
- **Layering claims → `[tool.pypeeker.import-boundaries]` in
  `pyproject.toml`**, cross-checked against actual imports with Grep if a
  claim looks stale.
- **Test-suite size → `find tests -name 'test_*.py' | wc -l`** (or
  equivalent) rather than trusting the last recorded count.
- **CI description → `.github/workflows/ci.yml`** read directly, not
  paraphrased from an old memory of it.
- **Self-lint zero-baseline claim → run it**: `uv run pypeeker index src &&
  uv run pypeeker check` (or `scripts/verify-repo.sh`) and confirm the
  gated rule set and finding count match what CLAUDE.md states.

Every claim must be checked against the repo, not against another doc's
description of the repo — architecture.md and this skill both derive from the
same source, so treat pyproject.toml and the tree as ground truth when they
disagree with prose anywhere else.

## Keeping the sweep cheap

A full audit touches many files across the repo and can burn a lot of main-
context budget on reads that are only needed transiently. When doing a
whole-repo sweep (as opposed to checking one or two claims), delegate it to a
read-only Explore subagent: hand it the list of claims to verify and have it
report back which are correct, which are stale, and the corrected values.
This keeps the main conversation's context clean for the edits that follow.

## Applying fixes

- **Targeted edits only.** Use Edit to correct the specific stale sentence,
  path, count, or table row. Never regenerate CLAUDE.md from scratch — that
  discards phrasing, structure, and intent that took care to get right, and
  makes the diff impossible to review.
- Match the existing prose style of the surrounding section (terse,
  declarative, cross-referencing architecture.md rather than duplicating it).
- Do not touch the generic Backlog.md CLI instruction text (between the
  `<!-- BACKLOG.MD GUIDELINES START -->` / `END` markers) — it is generated
  and regenerated by `backlog agents --update-instructions`, so edits there
  are overwritten. It is the *only* out-of-scope region, and it is scoped to
  those markers alone: everything above them is repo-owned prose and **is**
  in scope. If you find repo-specific content that has drifted inside the
  marked block, do not edit it in place — move it above the START marker
  first, then correct it there, and note the move in the summary.
- If a claim can't be verified (e.g. it depends on something outside the
  repo), say so explicitly in the summary rather than guessing.

## Finish with a summary

End every audit with a short report split into three lists:

- **Verified** — claims checked and confirmed accurate, unchanged.
- **Corrected** — claims that had drifted, with the old and new value and
  the file/line edited.
- **Removed** — claims that no longer apply to anything in the repo and were
  deleted rather than corrected.

If everything checked out, say so plainly rather than padding the report.
